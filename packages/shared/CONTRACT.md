# Aeneas foundation contract

Every client and the hub implement exactly this. Change this file first, then code. Types in `src/types.ts` are the machine-readable form of this document.

## 0. Principles

### The seven tenets (2026-11-06)

Every part of the app and the system follows these. A feature that cannot meet one says so where people choose it (its module note, its setup step or its own screen), names what leaves the device and to whom, and is off until they turn it on.

1. **Privacy by default.** Nothing personal is collected, logged or kept longer than the feature needs; logs hold routes and error codes, never personal text or secrets.
2. **No data sent to any company by default.** A fresh install talks to no third party until the person turns that on (a sign-in, a cloud model, a search through SearXNG). Known exception, chosen at install: Tailscale's coordination service sees which devices exist and when they connect, not what they send; home-network mode avoids it.
3. **Local where possible.** Work happens on the device or on the person's own hub (models, search, speech when the device can, maps lookups such as the meals tax state).
4. **Security by default.** One key per device, encrypted backups, pinned certificates, changes to a machine wait for an approval, permissions asked only for modules that are on.
5. **Cohesion.** One contract, one look and one way of doing things across hub, web, Windows and Apple apps; a feature exists on every device it makes sense on.
6. **Easily modded.** Every feature is a module that can be switched off; everything owner specific is a setting, not code; anyone can build and run their own copy of every part (`CONTRIBUTING.md`, `apple/README.md`).
7. **Wanting to help people.** Plain words, no dark patterns, no nagging; the app does the sorting and remembering so the person does not have to.

- One person per hub. Every device has its own key, got with a one-time pairing code; the hub's main key (`EA_TOKEN`) stays on the hub's machine for its own scripts (since 2026-11-05, `hub/src/devicekeys.ts`). Tailscale is the network boundary.
- Several people on one machine (since 2026-11-08, `deploy/people.sh`, `docs/multi-person.md`): each person gets their own hub in their own Linux account (`aeneas-<name>`, no password, no login, home mode 700), on its own port and Tailscale address (`https://<machine>:<port>`), with its own data, keys, notes, chats and backups. Hubs never share a database or files. What they share is the machine's model server, through the model gate (AI, below), and the owner's settings for how the model runs (`EA_OLLAMA_MODEL`, `EA_OLLAMA_NUM_CTX`, `EA_OLLAMA_KEEP_ALIVE`, `EA_OLLAMA_THINK`, `EA_BACKGROUND_AI`, `EA_SEARXNG_URL`, `EA_TOR_SOCKS`, `EA_TZ`). Another person's hub has no keys to the owner's machines and reads none of the machine's sensors (`EA_HOST_SENSORS=false`); the image service is the owner's only. Each hub has a name and a color (`EA_HUB_NAME`, `EA_HUB_COLOR` `#rrggbb`), which `/health` gives devices with a key; clients show them (a dot in the hub's color and "<name>'s hub" in the web app's sidebar and top bar and its window title, in Settings on every app) only on a hub with a color, so a single person's hub looks as before. Anyone with admin (root or sudo) rights on the machine can read every hub's files; the apps say so where people are added, and so do the README and `docs/multi-person.md`.
- Adding a person from the app (since 2026-11-08, `hub/src/hubs.ts`; Settings, People on this machine, on the owner's hub only): `GET /hubs` → `{ available, reason?: "linux_only" | "not_set_up" | "not_owner", setup_command, admin_note, hubs: [{ name, account, port, color, owner, address, up }] }` (`hubs` empty unless available). `POST /hubs` `{ name, color? }` (name: a letter, then letters, spaces, `'`, `.`, `-`, up to 30; 422 otherwise, 409 when taken or not available) → 202 `{ request_id }`. `POST /hubs/:account/pair` and `POST /hubs/:account/stop` (an `aeneas-*` account in the list, never the owner's; 404 otherwise) → 202 `{ request_id }`. `GET /hubs/requests/:id` → `{ state: "queued" | "working" | "done" | "failed", step?, error?, name?, color?, address?, account?, note?, pairing?: { hub, code, expires_at, app, web } }`. The hub writes each request into `/var/lib/aeneas/requests` (only the owner's account can); `aeneas-people.path` runs the root-owned `/usr/local/sbin/aeneas-people serve-requests`, which takes only `add`, `pair` and `stop` with checked fields and writes progress and results to `/var/lib/aeneas/results` (readable by the owner's account only). The hub never runs anything as root. Clients poll the request every 2 s, then show the address, the two steps left (share the machine on Tailscale; scan the pairing QR code on their phone) and the admin note. The assistant's tools can neither read nor change `/hubs`.
- Offline-first. Every client keeps a local copy of all entities it cares about and an outbox of patches. The hub is authoritative.
- Entities are JSON documents with a `kind`. Per-field last-writer-wins using the field's `ts`.
- Nothing is hard-deleted. `deleted_at` is a field like any other.
- Spaces: `personal` (default) and `work`. Work entities are only calendar events and tasks, never notes, and are excluded from AI egress unless the request says `allow_work: true`.

## 1. Entity envelope

```json
{
  "id": "uuid-v4",
  "kind": "capture | note | task | reminder | event | log | fact | rule | runbook | ledger | project | device | watch | plan_rule | journal | snippet | pet_event | sensor | reading | food_option | inventory | procedure | music_idea | quiz | monitor | incident | checklist | application | game | film",
  "space": "personal | work",
  "created_at": "ISO-8601 UTC",
  "updated_at": "ISO-8601 UTC",
  "deleted_at": null,
  "fields": { ...kind-specific, see section 2 },
  "field_ts": { "fieldName": "ISO-8601 UTC", ... }
}
```

`field_ts` records when each key inside `fields` was last written. Clients may omit `field_ts` on write; the hub sets it to the patch `ts`.

## 2. Kinds and their fields

Required fields are marked `*`. All text is UTF-8 without BOM. Dates are ISO-8601 with timezone. Durations are minutes.

### capture
Raw input from anywhere. Never edited in place; it is converted into something else and marked processed.
- `text*` string
- `source*` `watch | iphone | ipad | mac | windows | web | shortcut | voice | api`
- `transcript_confidence` number 0..1 (voice only)
- `attachments` array of `{ name, mime, bytes_b64 }` (small only; images under 2 MB)
- `processed` boolean, default false
- `converted_to` array of entity ids
- `suggested_kind` `task | note | reminder | log | fact | none` (set by the hub classifier)
- `sorted_by` `auto | manual`, set when the capture is processed: `auto` when the hub converted it (classifier or the Inbox note fallback), `manual` through `/capture/:id/convert`
- `thread` string, optional (since 2026-11-02): the assistant chat that filed it (`capture-<id>`, stored as the capture and the answer, titled "Capture: ..."). Unsorted Info links to it so a filing can be corrected in that chat.
- `sort` boolean, optional (since 2026-11-03): a device saved it with Save while the hub was out of reach (`processed: false`). The hub's filing job sorts it once it arrives, exactly as `POST /capture` with `auto: true` does, and sets `sort: false`.

### note
Stored as markdown on the hub (the notes folder, `EA_VAULT_DIR`) and shown to the user as plain text. The original Obsidian vault is imported once with the vault tool and then left alone.
- `title*` string
- `body` markdown string
- `tags` string[] (no leading `#`)
- `path*` folder path inside the notes folder, ending in `.md`, e.g. `Programming/App Ideas/Weather Bot.md`
- `links` string[] of note titles, derived by the hub on every write: explicit `[[wikilinks]]` plus any mention of another note's title in the body. The user never types links.
- `related` string[], optional (since 2026-11-03): titles of the notes the note linker found this one relates to. Part of `links`; written to the file's frontmatter as a `related:` list of `"[[Title]]"` items, which Obsidian shows in its graph and backlinks, and read back from it. Since 2026-11-05 a related note whose file is named otherwise is written `"[[file name|Title]]"` (Obsidian opens links by file name), and when a note is renamed the other notes' `related` follow it.
- `frontmatter_extra` string or null, optional (since 2026-11-05): the file's other frontmatter properties (`aliases`, `created`, `cssclasses`...), as written; the hub writes them back on every rewrite of the file. Double-quoted values in frontmatter are read back with their escapes (a title with quotes no longer gains backslashes).
- Files (since 2026-11-05): a note is never written over another live note's file: it gets `<stem> 2.md` and so on (its `path` changes, and devices learn it by sync), and deleting or moving a note removes only its own file. A file or folder name starting with a dot loses the dots (a hidden file is never indexed).
- `ai_tags` string[], optional: the tags in `tags` the note linker added (the others are the user's). `tags_rejected` string[], optional: tags the linker added and the user removed; never added again.
- `suggested_tags` string[] set by the hub (rule-based on every `/notes/:id/suggest`, model-assisted with `?ai=true`); accepted with `/notes/:id/accept`. Clients no longer show suggestions to accept: the note linker applies tags itself.
- `pinned` boolean
- `project_id` the project the note belongs to, set by the knowledge sweep for a note in that project's folder (its plan document, `Projects/<name>/`, or any folder named like the project); never written to the file
- Notes are shown to the user as plain text with a rich editor. Markdown is the storage format under the hood and the export format; clients never require markup.

### task
- `title*` string
- `notes` markdown string
- `status*` `inbox | next | scheduled | doing | done | parked`
- `order*` number (manual priority; lower is higher)
- `due` ISO date or datetime, optional
- `block` `{ start: ISO, end: ISO }` optional, the planned 3 to 4 hour block
- `project_id` entity id, optional
- `done_at` ISO, optional (for a repeating task, when it was last done)
- `parked_reason` string, optional
- Reminders are tasks (since 2026-10-28). A task can carry a deadline (`due`) and a reminder (`remind_at`), both optional:
- `remind_at` ISO datetime, optional: when to notify. A task with one and nothing else to do waits in `scheduled`.
- `repeat` string, optional, the reminder grammar below. Done on a repeating task moves `remind_at` (and `due`, keeping its distance) to the next occurrence and keeps it open.
- `friction` `none | reason`, optional (default `none`): `reason` requires a typed reason to snooze.
- `snoozed_until`, `snooze_log`, `fired` as for reminders below.
- `linked_id` entity id, optional: the item it is about (a renewal, a pet event, a job application); the hub keeps those tasks (`reminder_id` on the item points at the task).
- `apple` `{ id, list, list_title? }`, optional, written by the iPhone and Mac: the Apple Reminders item it mirrors. `id` is the calendar server's identifier, the same on every device; `list` is the writing device's list id. Every list syncs both ways (title, notes, due, reminder time, repeat for days and longer, done, deletes); lists from a work account become work-space tasks and are never deleted in Apple when the work space is erased. Only the iPhone adds Apple items for tasks made in the app. A task made inside a list carries `apple: { id: "", list: "", list_title }`; the iPhone adds it to the list of that name (a personal task without one goes to the default list; a work task without one stays out). Changing `list_title` on a linked task moves the Apple item when the change is newer than Apple's last edit. Clients show tasks by space (Personal, Work) and by list name.

### reminder
Older kind. The hub turns every live reminder into a task on start and on every reminder tick (same title, `at` as `remind_at`, repeat, friction, snoozes and link; finished one-off ones become done tasks; task id `stableId("task-from-reminder:<id>")`; items pointing at it are re-pointed) and deletes the reminder. Nothing new is written with this kind. Its fields, for reading old data:
- `title*` string
- `at*` ISO datetime, next fire time
- `repeat` string, optional. Format: `every <n> <minutes|hours|days|weeks|months|years>` optionally followed by `on <mon,tue,...>` for weeks or `on day<d>` (no space) for months. Examples: `every 1 days`, `every 2 weeks on mon,thu`, `every 1 months on day15`. Since 2026-11-05: `every 2 weeks on mon,thu` fires on those days of every second week counted from the week it started; months and years keep the day they started on, or the month's last day when it is shorter (Jan 31 to Feb 28, then Mar 31 when counted from the start); finishing a repeating task before its time moves it to the occurrence after that time; a `due` that is a date alone moves as a date. Task times (`remind_at`, `snoozed_until`, `due` with a time, `done_at`, `block`, `fired`) are stored in UTC: one sent with an offset is turned to UTC on the way in, since the hub compares them as text.
- `friction*` `none | reason`. `reason` requires a typed reason to snooze. (`witness` was removed on 2026-10-28; the hub changes stored ones to `reason` and reads any that arrive as `reason`.)
- Repeats keep local wall-clock time in the hub's `EA_TZ`, so a 09:00 reminder stays 09:00 across daylight saving changes.
- `snoozed_until` ISO, optional
- `snooze_log` array of `{ at: ISO, until: ISO, reason: string }`
- `fired` array of ISO datetimes the hub emitted a notification
- `acknowledged_at` ISO, optional (done for one-shot; resets on each repeat)
- `linked_id` entity id, optional (a task or event this reminder belongs to)

### event
Calendar event, mostly mirrored from outside (work calendar, EventKit import).
- `title*` string
- `start*` ISO
- `end*` ISO
- `all_day` boolean
- `source` `manual | m365 | eventkit`
- `external_id` string, optional
- `location` string, optional
- `apple` `{ id, calendar?, from_apple? }`, optional, written by the iPhone and Mac: the Apple Calendar event it mirrors. `id` is the calendar server's identifier, the same on every device. Events made in the app (`source` `manual` or absent) are copied into Apple Calendar: personal ones into the calendar the fact `calendar:personal` names (a calendar title or account address; else the default calendar for new events, unless that is a work calendar), work ones into the calendar `calendar:work` names (else not copied). Edits and deletions made in either place reach the other; an event found in the wrong calendar is moved. The Mac adds and moves at once, the iPhone after the event has been untouched for two minutes, adopting a copy that already exists. Imported events are never written back, and the work import skips the app's own copies. Events made in Apple Calendar's personal calendar (the one `calendar:personal` names) come into the app the same way: each single event from 30 days back to a year ahead becomes a `personal` event with id `uuid("apple-event:" + apple id)` (the same on every device) and `apple.from_apple: true`, after which edits and deletions travel both ways like an event made in the app; one is not moved back when the owner moves it to another calendar, and one deleted in the app is not brought back. The iPhone takes one after it is two minutes old (the Mac at once), and an event with the same title and start as an app event is that event's copy, not a new one. Its repeating events come in as occurrences (`source: eventkit`, `personal` space, same keys and window as the work import), never written back.
- Work calendar import (iPhone): the Apple app reads the calendars the user marks as work from the phone's Calendar store (EventKit) and upserts one `event` per occurrence in the `work` space with `source: eventkit`, `external_id` = the occurrence key (`eventIdentifier` plus start time), title, start, end, all_day and no location, notes or attendees. Window: 7 days back to 30 days ahead. Occurrences that disappear from the window are soft-deleted. Runs on launch, on foreground, on `EKEventStoreChanged`, and in background refresh.

### log
One-tap or passive measurements.
- `type*` `weight | med | bp | caffeine | sleep | mood | activity | steps | custom` (`steps` is a day's total, from Apple Health)
- The newest `weight` and `bp` logs are kept in memory by the hub: `fact` `weight:current` and `bp:latest` (category `health`, private, `source: "logs"`), value like `Weight 116.4 lb on 2026-10-30 (before that 118 lb on 2026-10-21)`. Any write or delete of such a log rewrites it, so deleting a wrong entry puts the one before back.
- `value*` number or string (bp is `"120/80"`; med is the med name; activity is the activity name; mood is -2..2)
- `unit` string, optional (`lb`, `kg`, `cups`, `min`). One unit per measure where it adds up (since 2026-11-05): caffeine is kept in cups of 95 mg (no unit is cups; `POST /log` and a capture turned into a log change a value in `mg` into cups, and logs stored in mg are changed once at start), since the iPhone writes each caffeine log to Health as cups times 95 mg; sleep is minutes, as Apple Health sends it, unless the unit says hours; weight is lb unless the unit is `kg`, and readers convert to one unit
- `name` string, optional: what a `custom` log measures (`pushups`); the dashboard groups custom logs by it, else by `unit`
- `at*` ISO
- `note` string, optional (an activity log whose `note` is `end` closes the activity started by the previous log with the same `value`; another start of the same activity while it is open is the same session, and an end with nothing open is ignored)
- `checkins` ISO[] hub-managed, when the hub asked whether a long activity is still on purpose
- `source` same enum as capture.source

### fact
Structured memory about the user. The assistant reads these before answering.
- `category*` `identity | constraint | preference | health | relationship | host | project | gear | history`
- `key*` string, unique within category (e.g. `host:pve1`, `diet:no_cook`, `dog:name`)
- `value*` string
- `source` string (where it came from, e.g. `seed`, `user`)
- `confidence` number 0..1
- `private` boolean. If true, never sent to a cloud model; local only.

### rule
A standing instruction for the assistant's output. Enforced by the style filter and injected into prompts.
- `text*` string
- `enforce` `prompt | filter | both`
- `pattern` string, optional JavaScript regex source the filter applies
- `flags` string, regex flags, default `g`
- `replacement` string, optional
- `active` boolean

### runbook
Per-host or per-system operational memory.
- `host*` string (hostname or system name, e.g. `pve1`, `storage`, `unifi`)
- `title*` string
- `body` markdown
- `commands` array of `{ label, host, user, command }`
- `last_verified` ISO, optional

### ledger
"Already tried" record for one troubleshooting session.
- `session_id*` string
- `topic*` string
- `tried` array of `{ at: ISO, what: string, result: string }`
- `ruled_out` string[]
- `confirmed` string[] (facts the user has verified; never re-ask)
- `open` boolean

### project
- `name*` string
- `parts` array of `{ name, qty, have?: number, inventory_id? }`, optional; the hub fills `have` and `inventory_id` by matching `inventory` names case-insensitively on every write
- `status*` `active | parked | done`
- `definition_of_done*` string
- `resume_card` markdown (what to do next time, written by the assistant at session end)
- `plan_doc_path` vault path, optional (living plan document)
- `repo` string, optional
- `area` `music`, optional (since 2026-11-03): a music project also shows in the Music section, with its ideas and a way to start one there; music ideas pick their project among music projects


### watch
A renewal or expiry to stay ahead of: certificates, subscriptions, prescriptions, insurance gaps, RMA windows, warranties, domains.
- `title*` string
- `category*` `cert | subscription | prescription | insurance | rma | warranty | domain | other`
- `due*` ISO date or datetime
- `lead_days` integer, default 7: the linked reminder fires this many days before `due`; the linked reminder exists only from 14 days before it fires (made by the daily watch job when it comes into that window), so a renewal months away is in Renewals and not in Reminders
- `repeat` string, optional, same grammar as reminders; `renewed` rolls `due` forward by it
- `probe_url` string, optional, an https URL; the hub reads the TLS certificate daily and sets `due` to its expiry
- `cost` number, optional; `url` string, optional (where to renew or cancel); `notes` string, optional
- `reminder_id` entity id, hub-managed; `last_probe` ISO and `last_probe_error` string, hub-managed
- `renewed_at` ISO, optional
- `autopay` boolean, optional (since 2026-11-03): it renews and pays by itself. An autopay watch has no linked reminder (none in Reminders), clients show "Autopay" and no Renewed button, and the daily watch job rolls a passed `due` forward by `repeat`. The mail filer sets it from a receipt (true) or what a notice says (`auto_renews`); the owner's own setting on a watch they made is kept.

### plan_rule
A standing constraint for the block planner. The planner never schedules inside a blackout, shows commitments as fixed, and prefers preferences.
- `title*` string
- `type*` `blackout | commitment | preference | info` (`info` is shown on the week and today views but never blocks scheduling; used for custody weeks)
- `days*` string[] of `mon..sun`
- `start*` `HH:MM` local; `end*` `HH:MM` local (end may be `24:00`)
- `alternating_anchor` ISO date, optional: the rule applies only on weeks that are an even number of weeks from the anchor's week (custody weeks)
- `note` string, optional
- `active` boolean, default true


### journal
Change journal: what was done to a host or system, when, and how to undo it. Written by the assistant as a side effect of helping, or by hand.
- `host*` string (hostname or system name)
- `at*` ISO
- `what*` string (one line)
- `command` string, optional (the exact command or UI action)
- `risk*` `low | medium | high` (high: destructive or hard to reverse)
- `rollback` string, optional (how to undo)
- `outcome` `planned | running | done | failed | interrupted | reverted`, default `done` (since 2026-11-13 the hub writes an approved command's entry as `running` before it runs, then `done` or `failed`; `interrupted` when it stopped at its time limit, or the hub stopped or restarted while it ran, so it may be half done)
- `session_id` string, optional; `runbook_id` entity id, optional
- `source` `close`, optional: written by a session close, which replaces only these entries when the session is closed again

### snippet
A reusable script or command with parameters at the top.
- `title*` string
- `os*` `linux | windows | macos | any`
- `language*` string (`bash`, `powershell`, `python`, `sql`, `text`)
- `body*` string; parameters appear as `{{name}}`
- `params` array of `{ name, default?, description? }`
- `tags` string[]; `host` string, optional; `source_session` string, optional
- `last_used` ISO, optional
- Saved without anyone writing them: when the owner's message in a chat says a fix worked (a statement, not a question, and not "still not working"), the hub saves the commands that fixed it. These are the changes it ran for them in that chat and the shell code blocks in its last reply. Each is saved with `tags: ["from-chat"]`, `source_session`, and the host and OS when known. A command already saved, or one holding a secret or a redacted value, is skipped. The reply ends with "Saved to Snippets: <titles>."


### pet_event
- `pet*` string (`Pepper`)
- `type*` `vet | med | incident | custody | weight | food | note`
- `at*` ISO
- `note` string, optional; `cost` number, optional; `next_due` ISO, optional (the hub links a reminder `lead_days` 1 before it, friction `none`)
- `reminder_id` hub-managed
- custody only: `with` `me | other` (where the pet went at this handoff), `cycle_days` integer 1 to 90, optional (default 14). The newest handoff answers custody: the hub sets its `next_due` to `at` plus the cycle (unless set by hand), clears `next_due` on older handoffs so one reminder exists (titled `<pet> handoff tomorrow`), and turns off an old `<pet> week` alternating rule. A change to the newest handoff's `at` or `cycle_days` moves a predicted `next_due` (and its reminder) with it, never one set by hand; deleting the newest handoff gives the one before it its prediction and reminder back. Past the predicted day with nothing logged, custody keeps alternating on the same cycle. `/pets/:name/summary` `custody` gains `since`, `cycle_days` and `handoff_id`.

### sensor
Configuration for one home sensor that posts readings.
- `name*` string, unique (`cabinet_temp`)
- `unit*` string (`C`, `%`, `lux`, `moisture`)
- `location` string, optional
- `min` number, optional; `max` number, optional; `alert` boolean, default true: a reading outside min..max emits `notify { kind: "sensor", name, value, unit }` once per crossing, and again when it returns inside
- `last_at` ISO and `last_value` number, hub-managed; `state` `ok | low | high | stale`, hub-managed (stale after `stale_minutes`, default 180)

### reading
- `sensor*` string; `value*` number; `at*` ISO; `unit` string, optional

### food_option
- `name*` string; `kind*` `delivery | restaurant | grab | home`
- `items` string[] (what to order); `tags` string[] (`protein`, `plant`, `sushi`, `spicy`, `sweet-sauce`, `tomato`, `fried`, `cheap`); `avoid` boolean (never pick)
- `rating` 1..5, optional; `cost` number, optional; `last_picked` ISO, hub-managed; `times_picked` integer, hub-managed
- `notes` string, optional (since 2026-11-02): who recommended it, who the owner went with, anything to remember; searchable, so the people it names show it on their page


### inventory
Parts, components and gear the user already has, so parts lists can be checked against it.
- `name*` string; `category*` `component | gear | material | tool | other`
- `qty` number, default 1; `unit` string, optional; `location` string, optional; `tags` string[]
- `project_id` entity id, optional (reserved for a project); `notes` string, optional

### procedure
A guided procedure shown one step at a time. The user says done; steps are never reordered or skipped.
- `title*` string
- `steps*` array of `{ text, command?, host?, user?, done_at? }`
- `current*` integer index of the step on screen, default 0
- `started_at` ISO, optional; `done_at` ISO, optional
- `source_session` string, optional; `project_id` entity id, optional

### music_idea
Songs, riffs, progressions and lyrics only (since 2026-11-03). Reference sheets, templates and settings are notes in `Music/Reference/` tagged `music` and `reference`: the seed creates the gain staging cheat sheet and a DAW session checklist there, and the seed and nightly sweep move any `reference`, `template` or `setting` music idea into a note (the types stay in the schema for older clients).
- `title*` string
- `type*` `riff | progression | lyric | song | template | setting | reference`
- `body` string (chords, tab, lyrics, settings, markdown)
- `key` string, optional; `bpm` number, optional; `time_sig` string, optional (`6/8`); `tuning` string, optional
- `status*` `idea | wip | done`, default `idea`
- `tags` string[]; `project_id` entity id, optional; `audio_ref` string, optional (a file name or URL)

### quiz
A nightly recall quiz built from the day's assistant sessions.
- `date*` `YYYY-MM-DD`
- `items*` array of `{ q, a, hint, topic, asked_at?, result?: "right" | "wrong" | "revealed" }`
- `source_sessions` string[]
- `completed_at` ISO, optional


### monitor
A thing the hub checks on a schedule from where it runs.
- `name*` string; `host` string, optional (links to the runbook)

- `expect` string, optional (http: status code or body substring; dns: expected address; backup: the most hours since each job's last good run, a plain number for the backup or the one job a target names, `verify=<hours>` and `restore=<hours>` for the others, comma separated; defaults 28, 200 and 900)

## 3. HTTP API

Base URL: `https://<hub>` on the tailnet. All routes except `/health` (and the few named as open below) require `Authorization: Bearer <key>`, where the key is the device's own (`ead1_` and 43 more characters) or the hub's main key; a device's own key is accepted in `?token=<key>` as well so `EventSource` can open `/live`. The main key (since 2026-11-06) works only in the header, and only from the hub's own machine (a loopback connection with no forwarding or Tailscale headers) or from a caller named in `EA_MAIN_KEY_FROM` (its address, or the `Tailscale-User-Login` that Tailscale Serve adds); elsewhere it answers 403 `{ main_key: "not_here" }`, and in a link 401 `{ main_key: "header_only" }` (unless `EA_MAIN_KEY_IN_QUERY=1`). Browser pages get CORS answers only from the hub's own clients: `tauri://localhost`, `http(s)://tauri.localhost`, `http(s)://localhost:5173` and `http(s)://127.0.0.1:5173` (dev), and `EA_CORS_ORIGINS`. `/app` answers with a Content-Security-Policy that allows only the hub itself (`app.ts`, `APP_CSP`). A device's key also tells the hub which device is calling, so its `last_seen` updates on every request. A removed device's key answers 401 `{ error: "unauthorized", device_removed: true }`: the device forgets its key and asks to be paired again. A key the hub does not know at all (its keys file was lost, or the hub was moved without it) answers 401 `{ error: "unauthorized", unknown_key: true }`: the device keeps its key, shows that the hub does not know it, and offers pairing again. The hub answers CORS preflight for any origin with `Authorization` and `Content-Type` allowed, because the tailnet, not the origin, is the boundary.

### Health
- `GET /health` without a key, or with a key the hub does not accept → `{ ok: true }` only (since 2026-11-06). With a device's key or the main key (as allowed above), in the Authorization header → `{ ok: true, version, time, db_seq, ai: { cloud: boolean, tools: boolean, model: string | null, images: boolean, web: boolean, hosts: boolean, voice_model: boolean, synced_sessions: boolean }, hub: { name: string | null, color: string | null } }` (`hub` since 2026-11-08: `EA_HUB_NAME`, else the profile's name; `EA_HUB_COLOR`, else null). Clients show the cloud switch only when `ai.cloud` is true, the image button when `ai.images` is true, and use hub-held chats when `ai.synced_sessions` is true.

- `GET /install` (no token) → an HTML page with an `itms-services` link for the iPhone build published by `deploy/publish-ios-build.sh`; `GET /install/{EverythingApp.ipa|manifest.plist|icon57.png|icon512.png}` (no token) serves those files from `<data>/install`. Nothing else is reachable without the token.

### Sync
- `GET /sync/changes?since=<seq>&kinds=task,note&space=personal&device_id=<id>` → `{ changes: Change[], seq: number, more: boolean }` (page size 500). With `more: true`, `seq` is the last seq in the page; with `more: false` it is the hub's latest seq. `device_id` is optional. Since 2026-11-02 a `since` past the hub's latest seq (the hub was restored from an older copy) is answered from the beginning with `reset: true`, so the device takes every entity again instead of waiting for the hub to catch up.
- `POST /sync/push` body `{ device_id, patches: Patch[] }` → `{ applied: [{ id, seq }], rejected: [{ id, reason }], seq }`. At most 500 patches per push; more is a 422 and nothing is applied. Request bodies over 2 MB are a 413: clients cut pushes to about 1.5 MB, and a single patch over the limit is set aside as refused so it never blocks the rest. A patch that changes nothing writes no change row and wakes no device. Clients pull even when a push fails.

Readings are high volume, so `/sync/changes` leaves kind `reading` out of the feed unless `kinds` names it explicitly (for example `kinds=reading`); readings past `EA_READING_KEEP_DAYS` are purged without tombstones.

Device liveness: whenever `/sync/changes`, `/sync/push` or `/live` carries a `device_id` that names a `device` entity, the hub updates that entity's `last_seen`. The write is throttled to once per 60 s per device and is silent: it goes straight to the row and produces no change row, so clients do not wake each other up by polling. Clients see the new `last_seen` the next time that entity changes for another reason or when they read `/status`.

```
Change = { seq: number, entity: Entity }
Patch  = { id, kind, space?, ts: ISO, fields: { key: value }, create?: boolean }
```

Push semantics: for each key in `fields`, if `ts > field_ts[key]` (or key absent) the value is applied and `field_ts[key] = ts`. A `null` value clears an optional field. Clients must keep their patch clock strictly monotonic (two writes in one millisecond would otherwise collide); the hub does the same for its own follow-up writes. `create: true` with an unknown id creates the entity. Setting `deleted_at` is an ordinary field. Every applied patch produces one change row. The response `seq` is the hub's latest sequence, so the client can pull its own echo and move its cursor.

### Live
- `GET /live?device_id=<id>` Server-Sent Events. Events: `change` (`{ seq, id, kind }`), `notify` (`{ id, kind: "reminder", title, at, friction }`), `ping` every 25 s. `device_id` is optional and feeds liveness (above).

### Entities (convenience over sync, same storage)
- `GET /entities/:id`
- `GET /entities/:id/related` → `{ items: { id, kind, title, why, at, lines? }[] }` (`lines`, since 2026-11-02: on a person, up to four lines of a mentioning note, a diary day above all, that name them), at most 40, links first, then newest: items this one points at (`converted_to` and any `*_id` field; `why` "Filed as", "About", "Project", "Diary", ...), items that point at it ("Captured", "About them", "In this project", "Links here"), and people by name. A person lists the events, captures, notes, tasks, places and other items whose text names them (facts that name them show with what the owner told the app about them instead) ("Mentions them"; full name, nickname, or a first name no other person has, as a whole word); any other item lists the people its text names ("Mentioned"). Apps show these as "Related" on an item's screen, and every link to an item opens that item.
- Diary: every capture is a line `- HH:MM text` in the note `Diary/YYYY-MM-DD.md`. A day runs from 4 AM to 4 AM: a capture before 4 AM goes to the day before (its lines sort after that evening's), and Today's "Today so far" shows that day until 4 AM. The assistant never changes a diary note's path, title or lines; something the owner says happened on another day goes on that day's calendar as an all-day event. Today shows today's lines as "Today so far"; Unsorted Info lists the last 7 days' filed captures with where each went (`filed`; a capture converted by hand gets `filed` from the hub, e.g. `Logs: weight`, and clients show "Sorted by hand" when only `converted_to` is set). The assistant's `diary` tool reads days (lines, that day's events and logs) by date range and words.
- `GET /entities?kind=task&status=next&space=personal&limit=100` (`limit` defaults to 100 and is capped at 1000)
- `POST /entities` body `{ kind, space?, fields }` → Entity (hub assigns id and ts)
- `PATCH /entities/:id` body `{ fields }` → Entity
- `DELETE /entities/:id` → sets `deleted_at`

### Capture
- `POST /capture` body `{ text, source, attachments?, auto?: boolean, id?: uuid }` → `{ capture: Entity, suggested_kind, created?: Entity[] }`. `id` (since 2026-11-05) is the capture's own id, made by the device: the same capture sent again after its reply was lost answers 120 with the capture the hub already has, sorted once (409 when the id belongs to another kind); a device that saves it locally instead uses the same id, so the push meets the same entity. With `auto: true` the hub converts the capture immediately using the classifier (reminder phrases; "todo"/"task" prefixes become tasks with status `next`; bare short verb phrases become `inbox` tasks; records said in plain words, `parseRecord` in packages/shared: "today I weigh 116.4", "weighed in at 72 kg", "bp 130 over 85", "slept 7 and a half hours", "8k steps", "took my claritin", "mood 4", where the whole text must be the record; else note or none) and marks it processed. When the rules return `none`, the hub asks the local model inside its classify timeout. When the model is not configured, unreachable or times out, and the text is at least 80 characters or contains a line break, the hub keeps it as a `note` anyway: `path` `Inbox/<first 60 characters of the first line, filesystem-safe>.md` (numbered `<stem> 2.md` and so on when that path is taken), `title` the first line, `body` the full text; the capture is marked processed with `suggested_kind: note` and `sorted_by: auto`. Shorter unclassified text, and text the model itself classified as `none`, stays an unprocessed capture.
- **Save and sort, since 2026-10-30:** with `auto: true` (and no `work:` prefix) every capture is first written as a line `- HH:MM <text>` into the day's diary note (`Diary/YYYY-MM-DD.md`, title `Diary YYYY-MM-DD`, tag `diary`; the capture gets `diary_id`). The assistant decides every capture (since the second change that day): the phrase rules above are only a hint in its prompt and a fallback, used when the model cannot be reached, or when it files nothing for a clear record (a weight, a dose) or a command at the start of the text (`remind me`, `todo:`, `note:`, `remember to`; since 2026-11-05 not for a task guessed from a first word like "Check out that sunset"), and `filed` then ends with "(filed by rule)" or "(the assistant was unavailable)". Each capture is marked `processed: true, filing: "pending"` (so it is not in Unsorted Info) and filed in the background by the assistant with its tools, one capture at a time: plans become calendar events, things already done with a day or with people become all-day events on the day they happened (the filer is shown the personal events from two days before to a week after, and changes one that is already the same plan or outing instead of adding a second), lasting facts go to memory, to-dos become tasks, measurements logs, several when several fit, nothing more for a passing thought. When done: `filing: "done"`, `filed` (one line, e.g. `Calendar: Dinner at Luigi's with Jamie; Memory: ...` or `Diary only`), `converted_to` the touched ids. A failure is retried (every few minutes, 3 tries, `filing_attempts`); after the third it shows in Unsorted Info (`processed: false`) while the hub keeps trying every 30 minutes, up to 50 tries, so a capture made while the model was away for hours is filed when it is back (since 2026-11-05). A capture is never queued twice. A rule-filed record or reminder is dated from when the capture was made, not when it was filed. A photo on a capture goes to the model with it and into the gallery's Saved pictures; a `work:` capture's photo is dropped with its text. Work items the filer made are counted in `filed` (`Work space: 1 item`), never named. `POST /capture/:id/file` files one now and answers with the capture when done. This replaces the earlier immediate rule conversion, model classifier and Inbox-note fallback for `auto` captures; the `work:` prefix keeps its sealed rule path. Calendar from captures and chat: a clock time or range is a timed event; only a day or part of a day is an all-day event on that date with the part of day in the title; time is blocked only when the owner asks.
- **Ideas, since 2026-11-03:** the filer is given the user's note folders (every folder holding a note, not `Diary` or `Inbox`). An idea for something to make (a story, film, book, sketch, game, app, invention, business) becomes a note in the folder that fits best with tags `idea` plus its form; a riff, progression, lyric or song idea becomes a `music_idea`; a film to watch becomes a `film` with `watchlist: true, watched: false`. `save_note` takes `tags`.
- **Note linker, since 2026-11-03** (`hub/src/note-linker.ts`, off with `EA_NOTE_LINKER=false`): in the background, only while no chat is using the model (a chat stops it, as for the mail filer), the local model reads each personal note outside `Diary/` once, and again only when its title, folder or text changes (table `note_analysis`, 3 tries per version), newest change first. It is shown the tags in use with counts and up to 60 other notes ranked by shared words, folder and tags. It sets 2 to 6 tags (existing ones preferred, new ones only for a subject none covers; `idea` for ideas), `related` (up to 5 titles of real notes), and for a note in `Inbox/` or the top level the folder it belongs in (one of the user's folders, else it stays), plus a short title when the title is only the start of its text (the file is renamed with it). The user's own tags are never removed. Writing the note rewrites its file with the tags and related links.
- With `auto: true`, text starting with `work:` always becomes a `task` in the `work` space (title from the rest of the first line, the full text as notes when it spans lines), and the personal capture's text is replaced so no work text stays in the personal space.
- `POST /capture/:id/convert` body `{ kind: task|note|reminder|log|fact, fields? }` → created Entity, capture marked processed.

### Reminders
- Work space switch (hub-only setting in `<data>/work-space.json`): `GET /space/work` → `{ enabled, events, tasks, other }`. `PUT /space/work` `{ enabled: true }` turns it on; `{ enabled: false, confirm: "erase work" }` turns it off and, in the same call, blanks and tombstones every `work` entity (so every device drops it), compacts the change feed and VACUUMs → `{ enabled: false, erased }`. While off, the hub refuses any write to the `work` space (409 from `POST /entities`, a `rejected` entry from `/sync/push`), `work:` captures keep no text, and the iPhone calendar import does not run.
- Work space key (since 2026-11-01): on the hub every `work` entity's fields are stored sealed with the work space's own key (AES-256-GCM, the entity id as associated data; the column holds `enc1:` and base64). The key is a 32-byte file at `EA_WORK_KEY_FILE` (default `<data>/work.key`; on core `~/.config/everythingapp/work.key`), owner-only and in no backup. Work items are kept out of the full-text index (which is plain text) and `/search` matches them by opening them. Erasing the work space destroys the key after tombstoning, so the nightly backups and the Litestream replica, which hold the items sealed with it, can no longer be read; a new key is made for later work items. On start the hub seals work rows an older hub left plain, and does the same inside existing nightly backups (keeping their file times). A work row sealed with a key that is gone reads as absent: a device sending it again with `create: true` replaces it, and an erase tombstones it. Moving an entity between spaces is a change even with no field changes. Devices are unchanged: the sync API carries plain fields over TLS.
- Feel (hub-only setting in `<data>/feel.json`, one for every device, written to a temp file and renamed over it so a failed write never leaves half a file): `GET /prefs/feel` → `{ motion, theme, palettes, shapes, images, shape_size, density, sound, volume, key, scale, synth, octave, follow_music, hold, drag_bend, app_theme, app_themes, appearance, effective: { key, scale, from: { id, title, key } | null }, options: { keys, scales, synths, themes, shapes, app_themes } }`. `PUT /prefs/feel` merges a partial body (lists are replaced whole) and returns the same shape; an invalid value refuses the whole body (422), as does choosing a theme that does not exist. Tap effects: `theme` is a built-in palette (`aurora | sunset | ocean | forest | neon | candy | mono`) or `custom:<id>` of one of `palettes` (`[{ id, name, colors: 1 to 8 #rrggbb }]`, up to 30, renamed by editing `name`); deleting the palette in use falls back to `aurora`. An older body `{ theme: "custom", colors }` becomes a palette `mine` named "My colors". `shapes` is any of `triangle | square | circle | hexagon | diamond | star | ring | spark`; `images` (`[{ id, name, enabled, type }]`, up to 24) are uploaded shapes: `POST /prefs/feel/images?name=<label>` with the raw PNG or WebP as the body (content-type `image/png` or `image/webp`, 512 KB at most; clients shrink to about 256 px and keep the alpha) → 201 and the feel; `GET /prefs/feel/images/:id` → the bytes; `DELETE /prefs/feel/images/:id`. A burst picks from the enabled shapes and enabled images; `shape_size` and `density` (0.5 to 2, 1 normal) scale size and count. Sounds: `key` is `C … B` with sharps; `scale` is `major | minor | major_pentatonic | minor_pentatonic | blues | dorian | phrygian | lydian | mixolydian | harmonic_minor | whole_tone | hirajoshi`; `synth` is `sine | glass | pluck | bell | marimba | chip | pad` (default `sine`); `octave` 2 to 6; `volume` 0 to 1. With `follow_music` the played key and scale (`effective`) come from the newest `music_idea` whose `key` names a note ("A minor", "Bb dorian", "F#m"). `hold` (default on): a press sustains its note until release, its level only easing down while held (a quick tap is a short note). `drag_bend` (default off): while pressed, moving up or down steps the note through the scale (after 12 points, one scale step per 44 points, gliding between) and moving left or right turns a low-pass filter knob that rests at 3.1 kHz (one octave per 30 points, left darker, right brighter); this works while a scroll is under way. Every tap plays a note; creating an item plays a rising arpeggio of degrees 0, 2, 4 with a larger burst; finishing a task or acknowledging a reminder plays the chord. App colors: `app_theme` is a built-in id from `options.app_themes` (`classic` changes nothing and follows `appearance` `system | light | dark`; the others carry `mode`, `accent`, `background`, `surface`, `text`) or `custom:<id>` of one of `app_themes` (same fields plus `name`, up to 20). Clients fetch it at launch and on return to the foreground, keep a local copy for offline use, and send each change at once. Two things stay on each device and never reach the hub: a computer (the Mac app, the Windows app, a browser with a mouse) plays notes only once its own "Also on this computer" switch is on (off at first), and `motion` alone decides shapes (the system's reduced motion setting is not consulted).
- `GET /vault/export` → every note as markdown files in a `.tar.gz` (hidden folders left out).
- `GET /export/csv/<kind>[?space=&<field>=<value>]` → every non-deleted item of one kind as CSV (RFC 4180, CRLF, UTF-8 without a byte order mark), oldest first. Columns: `id, space, created_at, updated_at`, then every field the rows use (title, name, text, type, value and similar first, the rest alphabetical). Lists are joined with `; `, objects are JSON, `attachments` is left out, and a text cell starting with `=`, `+`, `@` or a non-numeric `-` gets a leading `'`. 400 for an unknown kind.
- The reminder routes below take a task id (a task with `remind_at`).
- `POST /reminders/:id/snooze` body `{ until: ISO, reason?: string }`. Rejects with 422 if friction requires a reason and none given.
- Apple notification categories: `EA_REMINDER` (Ack, Snooze 10 min) for `friction: none`; `EA_REMINDER_REASON` (Ack, a text-input Snooze 10 min whose text is the reason) for `reason`. Apple apps ask for notification permission on first launch once configured, including the Watch.
- `POST /reminders/:id/ack` → done: with `repeat`, `remind_at` and `due` move to the next occurrence and the task stays open; otherwise `status: done`.
- `GET /reminders/due?within=<minutes>` → `{ reminders: Task[], now: ISO, until: ISO }`: every open task with a reminder whose effective time (`snoozed_until` when later than `remind_at`) is at or before `now + within`, overdue ones included, sorted by effective time. `within` defaults to 60 and accepts 0 to 10080. Meant for a notification strip that must not scan every reminder.

### Search
- `GET /search?q=<text>&kinds=note,task,runbook&limit=50` → `{ hits: [{ id, kind, title, snippet, score }], chats: [{ session_id, title, snippet, role, at, last_at }] }` (SQLite FTS5). Since 2026-11-13 `chats` are assistant chats with the text in their title or in what was said (the owner's and the assistant's lines, not tool results), newest first, at most 20, each with about 160 characters around the first match; deleted and internal chats are left out, and a search with `kinds` gets none unless `kinds` includes `chat`. Every kind people look for is indexed (notes, tasks, fix notes, captures, facts, projects, reminders, events, troubleshooting, change journal, snippets, procedures, renewals, job applications, games, films, inventory, music ideas, lists, plan rules, rules, food, Pepper); the hub rebuilds the index once after `ftsText` grows (SQLite `user_version`).
- `GET /calendar.ics?token=<token>` → the personal plan as an iCalendar feed for subscribing from any calendar app (`webcal://`): scheduled task blocks, personal events, pending reminders (15 minutes each) and renewal due dates (all day), 30 days back to 180 ahead, refreshed every 15 minutes; work items are left out. The apps offer it under Settings, Connections, Calendar. All-day items: a midnight with any offset, or a date alone, is that date (an all-day plan written before a clock change keeps its day), and a date-only end is exclusive. An item whose time cannot be read is left out of the feed instead of failing it (since 2026-11-05).

### Dashboard (charts of anything over time)
A board of tiles, one setting for every device. Everything here reads; nothing is written to the change feed.
- Metric ids: `log:weight` (in the newest weight log's unit, kg or lb, every reading converted to it), `log:sleep` (hours; minutes unless the log's unit says hours; an Apple Health night counts for the day it ended, its asleep time plus its minutes plus 6 hours as the iPhone names nights, a sleep log made in the app for its own day), `log:steps`, `log:caffeine` (cups; a log in mg counts at 95 mg a cup), `log:mood`, `log:med` (doses taken), `log:activity` (minutes, each activity session until its `end` log, split at midnight), `log:bp_systolic`, `log:bp_diastolic`, `log:custom:<name>` (custom logs by `name`, else `unit`, case-insensitive), `sensor:<name>` (its readings), `tasks:done` (by `done_at`, else when the status became done), `captures:created`, `monitor:<id>` (percent of checks ok; checks are kept 7 days).
- Each metric turns a local day (`EA_TZ`) into one number by its `agg`: `mean` (weight, mood, blood pressure, sensors), `last` (sleep, steps: day totals), `sum` (caffeine, activity, custom), `count` (meds, tasks, captures), `pct` (monitors).
- `GET /dashboard/metrics` → `{ metrics: [{ id, label, unit, group, agg, chart, count, last_at }] }`: only metrics with at least one reading. `group` is `Body | Logs | Plan | Home | Homelab`; `chart` is the suggested look.
- `GET /dashboard/series?metric=<id>&days=30` (`days` 1 to 365) → `Series`. 400 for an id that names no kind of metric; a well-formed id with no data (a sensor not yet posting, a deleted monitor) is an empty series.
- `GET /dashboard/board` → `{ tiles: [{ metric, range, chart, series: Series }], saved }`: the whole board in one read.
- `GET /prefs/dashboard` → `{ tiles: [{ metric, range: 7 | 30 | 90 | 365, chart: "line" | "bar" }], saved: boolean, options: { ranges, charts, max_tiles: 24 } }`, kept in `<data>/dashboard.json`. With nothing saved, `saved` is false and `tiles` are defaults built from metrics with data (weight, steps, sleep, tasks done, captures, activity, mood, caffeine, systolic over 90 days, up to three sensors and two monitors over 7 days; eight at most). `PUT /prefs/dashboard` body `{ tiles }` replaces the board in order (an empty list is an empty board); any invalid tile refuses the whole body (422). `DELETE /prefs/dashboard` goes back to the defaults. Clients send each change at once and keep the last board for offline display.

```
Series = {
  metric, label, unit, group, agg, chart, days,
  from: "YYYY-MM-DD", to: "YYYY-MM-DD",
  points: [{ day: "YYYY-MM-DD", value: number | null }],   // one per local day, today last; counts and sums are 0 on empty days, measured values null
  latest: { day, value, at? } | null,                      // counts and sums: today's number; measured values: the newest reading in the range
  period: "total" | "average",                             // total for count and sum, else average
  current: number | null, previous: number | null,          // the period and the same number of days before it (previous is null when it holds no data)
  change: number | null, change_pct: number | null          // current minus previous; as a percent of previous
}
```

### AI
- **Model gate** (since 2026-11-08, `hub/src/gate.ts`, `tsx src/main.ts gate`, the owner's user service `aeneas-gate`): on a machine with several people's hubs, every hub's `EA_OLLAMA_URL` is the gate (`http://127.0.0.1:11435`), which forwards to the model server (`EA_GATE_UPSTREAM`). Model runs (`/api/chat`, `/api/generate`, `/api/embed`, `/api/embeddings`, `/v1/chat/completions`, `/v1/completions`, `/v1/embeddings`) take one of `EA_GATE_SLOTS` places (default 1, Ollama's `OLLAMA_NUM_PARALLEL`); other paths pass straight through. The hub sends `x-aeneas-priority`: `chat` (someone waiting: chats, drafts, procedures, closing a chat; the default), `filing` (captures, the quiz, a sensor alert's troubleshooting), `background` (`backgroundJson`: mail, note tags, imports), `warm` (the assistant's warm-up). The queue goes by priority, then the person served longest ago, then arrival, so two people asking at once take turns call by call. A `chat` that finds every place held by background work stops the newest such call: 503 with `x-aeneas-gate: gave-way`, which the hub takes as a pause like one of its own chats stopping it (not a failure). A warm-up never waits: it runs only on an idle model nobody else used in the last two minutes (else 503 `x-aeneas-gate: busy`, `{ warmed: false }`). The caller is the Linux account owning the connection (`/proc/net/tcp`), not anything in the request. Only the gate's own account (the owner) may pull, push, create, copy or delete models; others get 403, and may run only the models in `EA_GATE_MODELS` (the owner's model). `GET /gate/status` → `{ gate: true, you, slots, running, waiting }`; the owner sees each call's account, everyone else only `priority`, `seconds` and `mine`. A hub whose model server is a gate (it answers `/gate/status`) sends the chat status "Waiting for the shared model" when other people's calls hold every place. The gate logs counts only.
- `POST /ai/chat` body `{ session_id, message?: string, images?: string[], approve_action_id?: string, messages?: [{ role, content }], task_type?: "auto | general | troubleshoot | draft | classify | plan", space?, allow_cloud?: boolean, allow_work?: boolean }` → `{ reply, model, backend: "ollama | anthropic | adapter", redactions, rules_applied: string[], session_id, mode, ledger_id?, procedure_id?, actions?: [{ tool, ok, writes }], pending_action?: { id, host, command, purpose, risk, preflight? }, images?: string[] }`.
  - Cloud (since 2026-11-03): a cloud backend is Anthropic or an OpenAI-compatible server whose address is not local. It is in the backend chain only when the request may use the cloud: `allow_cloud`, else `EA_ALLOW_CLOUD_DEFAULT`, else yes when a cloud model is the only one set up. Background jobs (mail, note tags, import learning, summaries asked with `allow_cloud: false`) never use one. With a cloud backend the memory leaves out private facts and work items, and every tool result has work-space items (`space: "work"` or `work: true`) and private facts taken out. Since 2026-11-05 every message bound for a cloud model, whatever made it (turns, tool results, the context note, summaries, voice drafts, resume cards), also has the values of private facts and the titles of work tasks and meetings (4 characters or more) replaced by `[withheld]`, and a cloud model's write to a work item is refused before it is made. A voice draft follows its chat's `allow_cloud`. An IPv6 address is local only when it is loopback, unique local (`fc00::/7`, the tailnet) or link local. `GET /ai/capabilities` `cloud` is true when any cloud model is set up.
  - **Hub-held chats (current clients):** send only the new turn in `message` (plus up to 4 base64 `images`, JPEG/PNG/GIF/WebP, 8 MB each, optionally as data: URLs). The hub stores the conversation, so any device continues any chat. Older clients and internal callers may still send the whole history in `messages`; the hub then trusts it as given.
  - **Auto mode** (`task_type` omitted or `auto`): the hub picks troubleshooting (ledger, host memory, pre-flight, procedures) when the conversation names a known host, reports a failure, or already has an open ledger; otherwise general. `draft` and `classify` stay explicit.
  - **History:** the hub never sends more than the model's context (`EA_OLLAMA_NUM_CTX`): an approved turn is counted with its command output, and tool results that would pass the context inside a turn are cut to fit (the head kept, with a note of how much was shown; command output from `run_command` and `approve_command`, and an approved turn's output, keep their head and their end, where errors are, and lose the middle). Turns that no longer fit are folded into a rolling summary stored on the session and carried in the system prompt; the newest turns go verbatim. The stream may send `status` events `{ type: "status", text }` (for example while condensing).
  - **Tools** (local model only, every mode but draft and classify): read and change every module, `remember` facts, `ledger_update`, `runbook_note`, generic `create_item`/`update_item`/`delete_item` over the kinds in section 2, `web_search` and `read_web_page` (when `EA_SEARXNG_URL` is set), `draft_in_my_voice` (the adapter backend), and host commands. The list is `hub/src/ai/tools.ts`.
  - **Host commands:** `run_command` runs read-only commands at once on hosts from core's `~/.ssh/config` plus `EA_HOSTS_FILE`. Any other command is held: the stream sends `approval` `{ type: "approval", action }` and `done` carries `pending_action`. Clients show the command with Run and Cancel. Run = a new `POST /ai/chat/stream` with `approve_action_id` (message optional, shown as "Yes, run it."); a typed or spoken "yes" also approves through the model. Since 2026-11-13 that approval (`approve_command`) runs only a change proposed before the owner's message it answers (one proposed in the same reply waits for their next yes), and a reply in which a change ran (by Run or by a yes) proposes no other; the next comes in a later reply. Cancel = `POST /ai/actions/:id/cancel`. Approved changes are written to the journal with their rollback before they run (`outcome: running`), then `done`, `failed`, or `interrupted` when stopped at the time limit; at start the hub marks commands its last run left running (a change that restarted the hub or rebooted its machine) `interrupted`, the action and its journal entry. Reads stop after `EA_COMMAND_TIMEOUT_S` (60 s), approved changes after 10 minutes; a command that times out is stopped with everything it started (its process group), and a result comes when the command exits even while something it left in the background holds its output. `sudo` is run as `sudo -n` only where it is the command a segment runs, never inside quoted text. Pending actions expire after an hour. Read-only (since 2026-11-03, `isReadOnly` in `hub/src/ai/hosts.ts`) means every part is a known reading command with no write option: no lone `&`, no redirect except to `/dev/null` or another stream, no `VAR=` prefix but locale and display settings, no command named by a path outside the system's own bin folders, `curl` and `wget` only to private, tailnet or bare host names, `sed` without `-i`, `w` or `e`, `awk` without `system`, a single `|`, `getline` or `print >`, docker groups only to their listing subcommands, and nothing naming a secret file (connections.json, hub.env, `.env`, keys, `.ssh`, the hub's data and key folders, `environ`, shadow, tokens, credentials, password managers). Since 2026-11-13 the command is read as the shell reads it (quotes and backslashes removed, line joins, comments to the end of the line, short option clusters such as `date -us` or `ss -tK`, GNU long options given shortened such as `sort --out=`), every unquoted `>` is a redirect (`->` and `=>` too), and these wait as well: here-documents, `$'...'`, brace expansion, `(` or `)` outside quotes on Linux and macOS (zsh, a Mac's login shell over ssh, runs code from `=(cmd)` and glob qualifiers; commands still run in each host's login shell), zsh's `$~x`, `$=x` and `$^x`, any variable but a few harmless ones (HOME, USER, LOGNAME, PATH, PWD, SHELL, HOSTNAME, LANG, TERM, TZ and the like), `ip` but its showing forms (global options skipped; `netns exec`, `netns attach` and `vrf exec` wait), `git branch`, `git tag` and `git remote` but listing, `nmcli` but its showing actions (and never `-s`), Windows `netsh` without `show` and `wmic /output:`, `/append:` and `/record:`, curl `--write-out` with `%output{}` or `@file` and `--variable`, OpenSSL `-out=`, `-engine`, `-provider` and `-config`, `docker compose config -o`, `@` in an awk program and gawk's file options, and reads that show secrets: `docker inspect` without a `--format` naming only fields (not `Config`, `Env` or `Options`), `docker compose config` but `--services` and the like, `ps eww` and `ps -E`, `jq` `env`, `systemctl show` without a property list, `launchctl print`, Windows `Env:` and `$env:` (but PATH, COMPUTERNAME, USERNAME and the like) and `key=clear`, recursive `grep`, `rg` over hidden files and `diff -r` of a home or a folder holding a secret file, and more secret files (gh's `hosts.yml`, Docker's `config.json`, `rclone.conf`, WireGuard configs, `tailscaled.state`, SSH host keys, saved Wi-Fi keys, shell histories, `.npmrc`, `.pypirc`, `.my.cnf`, TLS private keys, keytabs; `secret` and `token` count after `_` and `-` too). Every command starts with only PATH, HOME, USER, LOGNAME, SHELL, LANG, TERM, TZ, TMPDIR, SSH_AUTH_SOCK, XDG_RUNTIME_DIR and DBUS_SESSION_BUS_ADDRESS from the hub's environment, and its output, read or approved, has the hub's own secret values (its tokens, model and image keys, linked accounts' keys and tokens, the vault master password, the work key) replaced by `[secret]`.
  - **Reading pages** (since 2026-11-04): `read_web_page` reads public pages only. An address on the owner's network (private and tailnet ranges, loopback, link-local, 0/8, multicast, IPv6 unique-local, IPv4 inside IPv6, bare host names, .local, .lan, .internal, .ts.net) is refused, checked by the DNS lookup at every connection, so a redirect or a name that changes to a private address is refused too. Through Tor the exit does not reach private networks. Machines are read with host commands (Homelab).
  - **What tools may call** (since 2026-11-03, `hub/src/ai/api-guard.ts`): tools call the hub in-process with its token, but a path with a `.` or `..` part (plain or percent-encoded), a backslash or another host is refused with 403 before the router sees it, and so are reads of the KeePass master password and file, pairing links, the backup recovery key and the vault export, and writes under /connections (except `POST /connections/<steam|letterboxd|atlassian|google>/sync`), /space, /modules, /setup, /profile, /imports, /devices, /prefs/feel and /sync. `calculate` accepts only split, payoff, unit and takehome. A `backup` monitor target's destination is a host name or user@host (letters, digits, `._@-`, not starting with `-`); a ping target must start with a letter, digit or `[`.
  - Streaming variant: `POST /ai/chat/stream` returns SSE `token` events with data `{ "token": "<text>" }`, `tool`, `approval` and `status` events, then `done` with the same object as `/ai/chat`, or `error` with `{ error }`. Clients ignore event names they do not know. When no backend answers, `/ai/chat` returns 503 and the stream ends with `error`; the `error` text is written for the person and clients show it in place of the reply, never fail silently. The user's turn is stored even then.
- `GET /ai/sessions?limit=` → `{ sessions: [{ session_id, title, task_type, created_at, last_at, message_count, preview, working }] }`, newest first. `GET /ai/sessions/:id` → `{ session_id, title, task_type, created_at, last_at, messages: [{ role, content, at?, images?: string[], actions?, approval?: { action_id, host, command, status?, exit_code? } }], summary, summary_upto, pending_action, working }`; `pending_action` is the same `{ id, host, command, purpose, risk, preflight? }` the stream's `approval` event carries (since 2026-11-05; it had no risk or pre-flight lines). The hub stores the user's turn as soon as it arrives. `working` is `{ since, status, tool }` while a reply for that chat is still being worked on (from any device; `status` and `tool` are the latest status text and tool name) and `null` otherwise (`true`/`false` in the list). Clients that open a chat with `working` set show that the assistant is working and re-read the chat every few seconds until it clears. `PATCH /ai/sessions/:id` `{ title }`. `DELETE /ai/sessions/:id` erases the chat permanently (a reply still being worked on when it is deleted does not bring it back; two turns on one chat run one after the other): its messages, images only it used (except those the gallery keeps), host command output, AI call log, its troubleshooting ledger and procedures made from it (ledgers and procedures are blanked and tombstoned so every device drops them). `DELETE /ai/sessions` with body `{ "confirm": "wipe all chats" }` does the same for every chat and also erases the recall quizzes. Saved facts, runbooks and journal entries stay. Chats live in `chats.sqlite` (secure_delete, VACUUM after each wipe), which the nightly backups never include; `tsx src/main.ts purge-chat-backups [dir]` strips chat tables from backups made before that split.

- `POST /ai/classify` body `{ text }` → `{ kind, fields, via }` used by capture. `via` is `rules`, `model`, or `unavailable` (no model configured, unreachable, or timed out).

The hub sends the local model the start every chat shares, the system prompt and the tool list, with a one-token answer. It is skipped while a chat runs or within 3 minutes of the model's last use. `?wait=true` waits and answers `{ warmed, reason?, host?, read?, ms? }`. For the cache to match, the system prompt holds nothing that changes from chat to chat or with the mode: lists and checklists by name, rules oldest first, and the mode in the turn note.

### Devices
- `POST /devices/register` body `{ name, platform, push_token?, device_id? }` → `{ device_id }`. Called with a device key, it registers that key's device whatever `device_id` says.
- Pairing (since 2026-11-05, `hub/src/devicekeys.ts`):
  - `POST /devices/pairing` body `{ name? }` → `{ hub, code: "ABCD-EFGH", expires_at, fp, app: "everythingapp://setup?hub=&code=&name=[&fp=]", web: "<hub>/app/#/setup?hub=&code=&name=[&fp=]" }`, `cache-control: no-store`. `fp` is the SHA-256 of the hub's own TLS certificate (lowercase hex) when the hub address is https and the hub serves `EA_TLS_CERT`, else null; a client that gets it accepts that certificate only. The code is 8 characters of Crockford base32 (no I, L, O or U; typed case-insensitive with or without the dash, O read as 0 and I or L as 1), works once, and lasts 10 minutes or until the hub restarts. At most 5 wait at once. Links and QR codes never carry a lasting secret.
  - `POST /devices/claim` (no key: the code is the credential) body `{ code, name, platform, device_id?, push_token? }` → `{ device_id, key, name, version }`, `cache-control: no-store`. The key is shown this once; the hub keeps only its SHA-256, in `<data>/device-keys.json` (mode 600, a `.bak` copy before each write, in the encrypted settings archive sent to storage), not in hub.sqlite, so restoring the database from an older copy keeps every device paired. Removed keys are remembered by hash so the hub can say `device_removed`. A keys file that cannot be read is never written over: no device key works and pairing answers 500 until it is mended or removed. A Watch claimed with a code its iPhone made (with the iPhone's own key) is held by that iPhone: removing the iPhone removes the Watch's key and entry too. A wrong, used or expired code is 401 with a plain sentence, answered more slowly each time from the same address.
  - `POST /devices/exchange` with the main key, body `{ name, platform, device_id?, parent_id? }` → `{ device_id, key, name }` (`parent_id`: for a Watch, the iPhone that holds its key, so the Watch's key goes with that iPhone): a device paired before devices had keys trades the main key for its own and forgets the main key. With a device key it is 409.
  - `GET /devices` → `{ devices: [{ id, name, platform, last_seen, paired_at, own_key, current }] }`.
  - `DELETE /devices/:id` → `{ removed, also }`: its key stops working at once, its `device` entity is deleted, and so are the key and entity of any Watch it held (`also`). Deleting the entity any other way (sync, `DELETE /entities/:id`) does the same. A `/live` stream open with a removed key ends at once.


### Planner (Module 1: days and tasks)
Blocks are 3 to 4 hours by default. The hub plans inside `EA_DAY_START` and `EA_DAY_END` (defaults `09:00` and `23:00` local), minus `plan_rule` blackouts and commitments, minus existing task blocks and events.
- `GET /planner/week?start=YYYY-MM-DD&min_hours=3` → `{ start, days: [{ date, blocks: [{ task_id, title, start, end, status }], events: Entity[], commitments: [{ rule_id, title, start, end, type }], preferences: [{ rule_id, title, start, end, type }], reminders: Entity[], watches_due: Entity[], free_slots: [{ start, end, hours }] }] }`. `commitments` holds the blackout and commitment rules (they take time); `preferences` holds the preference rules (they rank free slots) and, since 2026-11-05, the info rules (they take nothing), for the clients to show; clients draw both by `type`. `start` defaults to the current week's Monday.
- `POST /planner/schedule` body `{ task_id, start: ISO, hours?: number (default 3), force?: boolean }` → the task with `block` set and `status: scheduled`. 409 with the conflicting block, commitment or blackout unless `force`.
- `POST /planner/unschedule` body `{ task_id }` → clears `block`; status becomes `next`.
- `GET /planner/today` → `{ date, now: Task | null, next: Task[], blocks, events: Event[], commitments, preferences (since 2026-11-05, as on the week), reminders_due: Entity[], watches_due_soon: Entity[], dates_soon: { id, name, label, date, days, years? }[], people_today: { id, name, plans: { id, title, at? }[], notes: string[] }[], captures_unprocessed, free_slots, digest: string }` where `events` are the day's events from every space (work meetings included, so a Work blackout shows what is inside it) and `digest` is a one to six line plain-text summary (since 2026-11-02 no "No blocks today" line); a `Plans:` line lists up to three of today's all-day events, a `Calendar:` line (`Meetings:` before 2026-11-02) up to four timed events still ahead today, a `Blocks:` line today's task blocks when there are any, and a `People:` line names up to two people today's plans name (with their first plan's time and the top note) and the dates within 7 days. `dates_soon` covers 14 days: every person's `birthday` and each entry of `dates` (`label` "birthday", "anniversary", another label, or "" for Apple's "other"; `years` is the age or anniversary count when the year is known; dates are YYYY-MM-DD or --MM-DD, Feb 29 falls on Feb 28 in other years). `people_today` lists the people named (full name, nickname, or a first name no other person has, as whole words) in today's plans: events not over yet (all-day ones all day), reminders due and tasks doing or due today, in the order of their first plan, at most six, each with every plan that names them and up to three of their facts' values, those sharing words with their plans first, then the newest. Apps compute both from their local data for Today's People section, so it works offline.
- At `EA_DIGEST_TIME` (default `09:00` local) the hub emits a `notify` event `{ kind: "digest", title, at }` once per day. Since 2026-11-02 `title` is the whole digest, one line each, the `Plans:` and `Calendar:` lines first; clients that show one line show the first. Since 2026-11-05 a `Homelab:` line names the enabled monitors that are down and the alerting sensors that are `low`, `high` or `stale` (a notify reaches only the apps open at that moment, so the morning says it again).

### Activity check-in
- Every 60 s the hub looks at the newest `log` of type `activity` with no closing `end` log for the same value (an older one still open counts too, even after a later activity started and ended). If it has run for `EA_FOCUS_CHECK_HOURS` (default 3) since the last check-in or start, the hub emits `notify` `{ kind: "activity", title: "On <value> for <h> h", log_id }` and appends to `checkins`. ### Memory and runbooks (Module 2)
- `GET /runbooks?host=` → runbooks, newest first; `GET /hosts` → `[{ host, runbooks, journal_entries, last_change, snippets }]` derived from runbook, journal and snippet entities plus `fact` keys `host:<name>`.
- `POST /snippets/:id/render` body `{ params: { name: value } }` → `{ text }` with `{{name}}` replaced (defaults fill the rest; 422 lists missing names); sets `last_used`.
- `POST /snippets/:id/run` body `{ params?, host? }` → `{ host, command, exit_code, output }`: renders, then runs on the snippet's `host` (or `host`) only when the rendered text is read-only (the assistant's check, so a parameter cannot slip a change in); 409 when it changes something (the assistant runs those after approval), 422 for a non-shell language or an OS mismatch, 404 for an unknown host. The seed adds four read-only examples tagged `example` (disks over a threshold, biggest folders, a service log, a port check), created once by title.
- `POST /ai/sessions/:id/close` body `{ outcome: "fixed" | "abandoned" | "parked", note?: string, host?: string, project_id?: string }` → `{ runbook_id?, journal_id?, snippet_ids: [], resume_card_written: boolean, summary }`. The hub derives the host from `host` or from host names in the session that match `fact` keys `host:<name>`, asks the model (when available) for: a dated runbook section (`## YYYY-MM-DD: <problem>` with symptoms, root cause, the fix, verification), one journal entry per change that was made with its risk and rollback, and up to two snippets for commands worth keeping; without a model it writes a rule-based summary (last user messages and ledger). It appends to the host's runbook (creates `Runbook: <host>` when missing), creates the journal entries, closes the ledger, and writes `project.resume_card` when a project is given or mentioned. Idempotent per session: a second close updates the same runbook section and does not duplicate journal entries. Since 2026-11-13 the entries a close writes carry `source: close`, and a second close replaces only those (and an older close's, which carry a `runbook_id`): pre-flight rows, the hub's entries for commands it ran, and entries the assistant (`journal_entry`) or the owner wrote stay. - Hum to MIDI (since 2026-11-03, `hub/src/hum.ts`, module `music`): `POST /music/hum?mode=melody|rhythm&bpm=&title=&project_id=&from=capture&client_id=` with the recording as a WAV body (16, 24 or 32 bit PCM or 32 bit float, any rate, mono or stereo; up to 2 minutes and the 25 MB upload limit; clients send 22,050 Hz mono 16-bit) → 202 with the new `music_idea` (`type: riff`, tags `hummed` and the mode, `audio_ref: hum:<id>`, `midi: { source: "hum", mode, state: "listening", seconds, notes: [] }`). ### Homelab ops (Module 6)
- The hub runs every enabled `monitor` at its interval from its own host: `ping` (ICMP through the system `ping` binary, 1 packet), `tcp` (socket connect), `http` (GET; ok when the status is 2xx or 3xx, or equals `expect` when numeric, or the body contains `expect` when text), `tls` (certificate valid and not expiring within 14 days; `last_error` carries the days left), `dns` (resolve; ok when any address is returned, or equals `expect`). After `fails_before_down` consecutive failures the state becomes `down`, an `incident` opens, and the hub emits `notify { kind: "monitor", name, state: "down", error, incident_id }` (since 2026-11-13 `incident_id` names the open incident, on the first alert and each re-notify, so apps can acknowledge it from the notification: iPhone, Watch and Mac show an Acknowledge button, the web banner too); the first success afterwards closes the incident (`closed_at`) and emits `state: "up"`. Since 2026-11-13 a machine that stops answering is one incident: a monitor that would go down while every enabled ping monitor on the same `host` is down joins the incident one of those pings opened instead (its `joined_incident` is set, its name goes into the incident's `also_down`, no alert of its own, and it comes back up without an alert). When the machine's last ping goes down, unacknowledged incidents of other monitors on that host opened in the 15 minutes before close into the machine's incident (`merged_into`) and those monitors join it. When the machine's incident closes, the monitors still down under it start counting failures again, and open their own incident (with an alert) only after `fails_before_down` more. A re-notify says `<name> still down since <local time> (<hours>): <error>`. A check of a monitor already being checked (by the loop or by hand) returns that check's result, the state is decided from the monitor as it is when the check ends, and the loop starts each due check on its own (at most 8 at once) without waiting for slow ones. A machine away counts from `last_reached` (the last check that reached it, failed or not), else from when the monitor was made, so one never reached fails after 72 hours instead of staying unknown. A failing service on a machine that still answers ping opens its own incident as before. `GET /ops` shows the machine's incident as `incident_open` on each monitor that joined it, and a re-notify adds `; also down: <names>`. A `down` incident re-notifies every 6 hours until acknowledged (`renotified_at` on the incident, kept across restarts). An incident whose monitor is deleted or off closes. A monitor that is off can be checked by hand (`last_error`, `last_ok` move) but opens and closes nothing. `tls` also needs a certificate a browser accepts (the chain verifies and the name matches; `last_error` `certificate not trusted: <reason>`), unless `expect` is `self-signed`; a renewal watch's `probe_url` with an untrusted certificate keeps its `due` and sets `last_probe_error`.
- `GET /ops` → `{ monitors: [{ ...monitor, incident_open: Incident | null }], incidents_open: Incident[], incidents_7d: number, uptime_24h: { name, pct }[], watches_due_30d: Watch[], journal_recent: Journal[] (last 10), hosts: from /hosts, hub_backup: [{ label, ok, at?, text }] }`. `hub_backup` (since 2026-11-13) is the hub's own backups beside the machines': "Nightly copy" (the newest encrypted backup, ok within 30 hours, `text` says how many are kept), "Second copy" (`EA_BACKUP_COPY_DIR`, when set), and on Linux "Copy to storage" (the `everythingapp-backup` user service's last run) and "Live copy" (the `everythingapp-litestream` user service running) when those units are installed; read at most once a minute.

- `POST /incidents/:id/ack` body `{ note?: string }` → sets `acknowledged_at`; with a note also writes a `journal` entry (host from the monitor, risk `low`, what `Incident acknowledged: <name>`, note as the command field is not used; put the note in `what` after a colon) and links it.
- `backup` reads a machine's ProjectBackup jobs (kopia to a backup server) over ssh from the hub's host, all in one login, with `BatchMode`, and only reads: on `mac` the launchd job (default `local.projectbackup.snapshot`, or `local.projectbackup.verify`) and `~/Library/Application Support/ProjectBackup/logs/backup.log` (or `verify.log`); on `windows` the scheduled task (default `Project Backup Snapshot`, or `Project Backup Verify`), `%LOCALAPPDATA%\ProjectBackup\backup-status.json` and its `Logs`; on `linux` the systemd unit (default `project-backup.service`, `project-backup-verify.service` or `project-backup-restore-test.service`) and its journal for 40 days. The names are settings, `job=name` pairs separated by commas, a job left out keeping its default: `EA_BACKUP_MAC_JOBS` (`backup`, `verify`), `EA_BACKUP_WINDOWS_TASKS` (`backup`, `verify`) and `EA_BACKUP_LINUX_UNITS` (`backup`, `verify`, `restore`); a name with characters outside letters, digits and `._-` (Windows also spaces and parentheses, Linux also `@` and `:`) is refused and the default kept. Since 2026-11-13 a target without `#job` reads every job the machine has (backup and verification, on linux also the restore test), so a machine is one monitor, one incident and one alert; a verification or restore test the machine does not have (no launchd job, task, unit or log of it) is left out, and a missing backup job, or a missing job the target names, fails with `no <job> job on <dest> (looked for <name>)`. The monitor is ok when every job it has is, and `last_error` names each failing job. Each job is ok when its latest finished run succeeded and its last good run is within its hours from `expect`; a run in progress is ok while the last good one is still that recent and no run failed after it (a retry after a failure stays down until it finishes well). Kopia's snapshot list is not used, because kopia skips saving a snapshot when nothing changed. The error says when the failing run was and why (kopia's error summary, failing sources, the systemd result or the exit code); times in `last_error` and `last_detail` are the hub's local time (`Nov 13, 3:17 AM`, since 2026-11-13; UTC before). On Windows a status file that says `running` is a run in progress and never a failure (its placeholder `success: false` opened false incidents); still `running` more than 2 minutes after the run began while the task is not running is a run `stopped before it finished`. At start, one-job monitors (`#verify`, `#restore`) beside a machine's backup monitor are folded into it (their hours into its `expect` when not the defaults, the longest timeout kept) and deleted, unless that monitor was already checked as a whole (it has `jobs`). An unreachable machine (ssh exit 255, or no answer in `timeout_s`) is a skipped check: no `checks` row, no failure count, no state change, `last_error` says so, and the relative age in `last_detail` is dropped. A machine that answers and refuses the login (exit 255 with `Permission denied`, `Host key verification failed` and the like) is a failure. Skips end after 72 hours with no good check (`last_ok`): the check then fails with "nothing checked for N days".

### One-door keys (since 2026-11-03)
Places that cannot keep the hub token private get a key that opens one door (`hub/src/feedkeys.ts`, `<data>/feed-keys.json`, 0600): `calendar` reads `GET /calendar.ics?key=` and nothing else (calendar apps sync the address to their cloud), `sensors` posts `POST /sensors/<name>/readings?key=` (or header `x-ea-key`) and nothing else (the key sits on a board and may travel in plain HTTP). `GET /feeds` → `{ calendar: { key, path }, sensors: { key, path } }` (made on first read); `POST /feeds/<calendar|sensors>/rotate` → the same with a new key, ending the old one. The hub's main key (and any device key) still works on both doors, so existing subscriptions and boards keep running until they are moved. Clients show only these keys in the calendar link and the sensor how-to. The assistant's tools cannot read /feeds, and the keys are hidden in command output like the hub's other secrets. The Apple app logs only a link's scheme and host. A pairing link (`everythingapp://setup?hub=&code=` or `#/setup?hub=&code=`, since 2026-11-05 carrying a one-time code; an older link with `token=` is traded for the device's own key at once) connects at once on a device that is not set up, or that already uses that hub; a link to another hub first asks "Switch this device to another hub?" with Switch hubs and Keep the current hub, so a link in a note, a page or an email cannot move a device unnoticed.

### Modules (since 2026-11-03)
Every part of the app beyond the core is a module the owner switches on or off, one setting for every device. The core is always on: Today, Assistant, Capture, Search, Unsorted Info, Tasks, Week, Notes, Memory, People, Lists, Settings, Status.
- `GET /modules` → `{ modules: [{ id, title, summary, group, on, reads?, permissions?, setup? }] }`, in display order. `group` is the Library area (`Plan`, `Homelab`, `Making`, `Body and home`, `Life admin`), `Assistant` for something the assistant may do that has no screen, or `On your devices` for a device feature with no screen of its own. Since 2026-11-05: `reads` says in one sentence what personal data it reads and from where (shown in setup); `permissions` lists what a device asks for while it is on, from `microphone`, `speech`, `notifications`, `reminders`, `calendar`, `contacts`, `health`, `photos` (a device asks right after setup or when the module is switched on, only for modules that are on, and never at launch); `setup` `{ minutes, needs }` marks a part that needs the person's own key or app ("your own Steam key, for playtime"), shown as a different level of setup.
- `PUT /modules` `{ "<id>": true | false, ... }` → the same list. An unknown id or a value that is not a boolean is 422. Switching a module on runs the seed files that module owns (food options, music reference sheets, snippets, monitors, runbooks) when they are missing, and no others, so a starter item the owner renamed does not come back as a copy (since 2026-11-05).
- `/live` sends `event: modules` with `{ modules: [...] }` whenever a switch changes, so other devices update at once. Clients ignore unknown event names.
- Ids and what they hold (screens per client; hub path prefixes in brackets): `renewals` Renewals [/watches, /finance], `dashboard` Dashboard [/prefs/dashboard], `homelab` Ops, Machines, Change journal, Snippets [/ops, /monitors, /incidents, /hosts, /snippets, /runbooks, /preflight, /ledgers, /connections/password-manager], `projects` Projects, Procedures [/projects, /procedures], `music` Music [/music], `wiki` Wiki [/wiki, /connections/atlassian], `images` Images, Image Gallery [/images], `quiz` Recall quiz [/quiz], `health` Health, Logs [/health, /imports/health], `pet` Pet [/pets], `food` Food [/food], `sensors` Sensors [/sensors], `games` Games [/games, /library/games, /connections/steam], `films` Films [/library/films, /connections/letterboxd], `calc` Calculators [/calc], `jobs` the Jobs list in Lists [/applications, /library/applications], `layouts` Layout sketches [/layouts], `mail` Gmail receipts read for renewals and pet visits [/connections/google], `web` the assistant's web lookups (no screen). On your devices (no hub paths; the Apple apps stop the matching work and do not ask for its permission while it is off): `voice` speaking captures and questions (microphone, speech recognition on the device), `notifications` reminder alerts, `apple_reminders` the two-way Apple Reminders sync, `apple_calendar` Apple Calendar events in and planned blocks out, `contacts` the Contacts mirror in People.
- Off means: clients hide its screens, Library rows, Today and dashboard parts; its hub paths answer 404 `{ error: "<Title> is off. Turn it on in Settings, Modules.", module }`; its background jobs pause (monitors and `homelab`; host and home sensor ticks and `sensors`; the daily renewal check and `renewals`; quiz, gallery collection, Steam, Letterboxd and Confluence syncs); mail is listed and read only while `mail` is on and `renewals` or `pet` is on, and files only into those that are; the assistant gets none of its tools or guide lines and `create_item` refuses its kinds; the capture filer is not told about it and phrase rules for its kinds do nothing. Its data is kept and synced as before: switching it back on shows everything again.
- Since 2026-11-05, while a module is off: the reminder tasks the hub keeps for its items (a renewal's, a pet event's, a job application's follow-up) are deleted on every device and made again from the items when it is switched back on, and its item hooks do nothing; renewal dates stay out of the calendar feed, `/ops` (`watches_due_30d`) and `/status`; a renewal or vet mail the model reads is parked (`state: parked`, `result.parked_for`) and queued again when its module is switched on; `GET /search` and the assistant's `list_items`, `get_item` and `search` leave its kinds out; with `homelab` off a waiting host command is not run on approval (409), `/ai/hosts` answers 404, and chats and session closes write no snippets, journal entries or fix notes.
- `<data>/modules.json` holds the switches. It is written the first time the hub reads it: a hub that already holds anything the starter seed does not make (captures, tasks, events, logs, notes, people, incidents, readings, pet events...) starts with every module on, so an update never hides what someone used; a damaged or unreadable file is left as it is for the owner to mend and logged, and every module counts as on meanwhile; a new hub starts with `voice`, `notifications`, `renewals` and `web` on, or with `EA_MODULES` (`all`, or a comma list of ids). A module missing from an existing file (one added after the file was written) has its default, except the ones that were always-on features before they became modules (`voice`, `notifications`, `apple_reminders`, `apple_calendar`, `contacts`, `mail`), which count as on so an update never turns off what the owner used.

### Layout sketches (since 2026-11-05)
Module `layouts`. A picture of a screen from any device with parts of it lifted and moved, resized or taken away, and new boxes drawn in, to show how the screen should be laid out. Not entities: they stay on the hub (`<data>/layouts/<id>.json`, pictures in `<data>/layouts/pictures/` stored once by hash) and never sync.
- `POST /layouts/pictures` with the raw picture as the body (PNG, JPEG or WebP, 20 MB at most) → 201 `{ picture_id, width, height }`. The size is read from the picture. Another type is 422.
- `GET /layouts/pictures/:picture_id` → the bytes.
- `GET /layouts` → `{ layouts: LayoutSummary[] }`, latest change first, deleted ones left out. `LayoutSummary` is a `Layout` without `pieces` and `deleted_at`, with `pieces_count`.
- `POST /layouts` `{ title, platform, screen?, picture_id, note?, pieces? }` → 201 `Layout` with `status: "draft"`. `GET /layouts/:id` → `Layout`; `PUT /layouts/:id` `{ title?, platform?, screen?, note?, pieces?, status?, after_id? }` → `Layout`; `DELETE /layouts/:id` → `{ ok: true }` (kept on disk with `deleted_at`).
- An unknown field, a picture id the hub does not have, two pieces with one id or a piece with neither `from` nor `to` is 422. At most 300 pieces.

```
Layout = {
  id, title, screen, note, picture_id, created_at, updated_at: string,
  platform: "iphone" | "ipad" | "mac" | "watch" | "windows" | "web" | "other",
  status: "draft" | "ready" | "done",       // ready: the owner is done arranging; done: it was built
  width, height: number,                     // of the picture, in its pixels
  after_id: string | null,                   // a picture of the arranged result, made by the client
  pieces: LayoutPiece[],
  deleted_at: string | null
}
LayoutPiece = {
  id: string,
  from: Rect | null,   // the part of the picture it is; null for a new box
  to: Rect | null,     // where it goes, in picture pixels (it may lie outside the picture); null to take it away
  label?: string,      // text on a new box, or a name for a part
  note?: string
}
Rect = { x, y, w, h: number }   // w and h above 0
```

### Backups and encryption at rest (since 2026-11-05)
Release rule 6. The live `hub.sqlite` stays a plain SQLite file, because Litestream reads it to replicate; the machine's own disk encryption (FileVault, LUKS) protects it, and the hub reports whether it is on. Every copy of the data that leaves that file is encrypted with age (X25519) to the hub's backup key, so the owner can also decrypt with the standard open-source `age` tool.
- Backup key (`hub/src/backupkey.ts`): an age identity the hub makes on first start at `EA_BACKUP_KEY_FILE` (default next to the work key: `<data>/backup.key`; on core `~/.config/everythingapp/backup.key`), mode 600, in the format `age-keygen` writes (`# created`, `# public key: age1...`, `AGE-SECRET-KEY-1...`). It is in no backup or copy. Written atomically and never over an existing file; a key file that exists but cannot be read or holds no usable identity is an error that changes nothing (backups stop and say why, the hub still serves). The identity itself is the recovery key the owner keeps in their password manager.
- Nightly backups: `VACUUM INTO` a `.partial` file, encrypted to `<EA_BACKUP_DIR>/hub-YYYYMMDD-HHMMSS.sqlite.age` (mode 600), the plain copy removed, 30 days kept (by file time). Plain `hub-*.sqlite` backups an older hub wrote are encrypted once, at start and each night, but only after the owner has saved the recovery key (`POST /setup/backup/saved`); until then they stay on the hub's own disk as the copies that open without it (the `encrypt-backups` command converts them at once when the owner runs it), after their work items are sealed and the chat tables of copies made before chats moved out are dropped, keeping their file times; the plain file is removed.
- Backups also (since 2026-11-06): a hub that was off at 03:00 makes the missed backup 10 minutes after it starts when the newest encrypted one is over 26 hours old; `EA_BACKUP_COPY_DIR` names a second folder (an external drive, a mounted share) each backup is copied to, with copies there over 30 days pruned (only `hub-*.sqlite.age` files; anything else there is left). The folder is never made: when it is missing the copy is skipped and logged. `deploy/restore.sh` checks a backup opens and is whole before stopping the hub, keeps the live database as `hub.sqlite.before-restore-<time>`, and asks for the recovery key (without echo) when the backup was made with another key; `deploy/uninstall.sh` removes the services and the programs the installer marked, and keeps the data and config folders.
- `GET /setup/backup` → `{ encrypted, recipient, recovery_saved, backups: [{ file, at, bytes, encrypted }], disk: { encrypted: boolean | null, detail } }`. `encrypted` is true while every backup on disk is encrypted (a plain one an older hub left is encrypted at the next start or night). `recipient` is the key's public half (`age1...`). `recovery_saved` is true once the owner marked this key's recovery key saved (a new key asks again). `backups` are newest first. `disk.encrypted` is null when the hub cannot tell, with the reason in `detail`: macOS reads the data folder's volume (`diskutil info`, FileVault, else `fdesetup isactive`), Linux the folder's mount source (`findmnt`) on a `crypt` device (`lsblk -s`), ZFS encryption, eCryptfs or fscrypt; every command has a 3 s limit and the answer is kept 10 minutes. A key file that cannot be read answers 500 with what to do.
- `POST /setup/backup/reveal` → `{ recovery_key }` (the identity, `AGE-SECRET-KEY-1...`), with `cache-control: no-store`, for the owner to save in their password manager. Never logged; the assistant's tools cannot reach it. `POST /setup/backup/saved` → `{ recovery_saved: true }`, kept in `<data>/backup-recovery.json` with the public key it was saved for.
- Commands (`tsx src/main.ts`): `restore <hub-...sqlite.age> <new path>` decrypts with the key file and, on a new machine, with the recovery key in `EA_RECOVERY_KEY` (`read -rs EA_RECOVERY_KEY; export EA_RECOVERY_KEY`), checks `integrity_check`, and never writes over a file. Without the hub: `age -d -i <file with the recovery key> hub-....sqlite.age > hub.sqlite`. `backup-key` prints `recipient=` and `file=` (never the identity). `encrypt-backups [dir]` seals and encrypts plain backups in a folder.
- Copy to storage (`deploy/user-backup/backup-to-storage.sh`): sends the newest `.age` backup and mirrors `<data>/outbox/` to `<storage>/encrypted/`: `settings.zip.age` (profile.json, modules.json, dashboard.json, feel.json, hosts.json, work-space.json and the Feel image shapes in one zip), `gallery/<file>.age` for each picture a live gallery record keeps and `audio/<file>.age` for each recording. Each picture and recording is encrypted once and again only when it changes; one whose source is gone leaves the outbox and the mirror. Sign-ins, the password vault, ai.json and both keys never leave.
- Litestream: the replica config holds the recipient and `${EA_LITESTREAM_AGE_IDENTITY}`; `deploy/litestream/litestream-with-key.sh` puts the identity in Litestream's environment from the key file when it starts, so it is never written to a config. Litestream 0.3.13 needs it while replicating as well as for a restore: on every start and after any failed sync it reads back the replica's last WAL segment (`calcPos`). An encrypted replica goes to a new path (`litestream-age`); a plain replica cannot be switched in place.

### Status and metrics
- `GET /status` → `{ version, started_at, uptime_s, db: { path, bytes, seq, entities_by_kind }, devices: [{ id, name, platform, last_seen }], backups: { dir, latest_file, latest_at, count }, ai: { backends_configured, calls_24h, last_call_at, last_backend, avg_latency_ms_24h }, reminders: { due_next: Reminder | null, fired_24h }, home: { sensors, sensors_alerting, readings_24h, pet_events_30d, food_options }, captures_unprocessed }`. `entities_by_kind` counts non-deleted entities. `db.bytes` includes the WAL file. `backups` counts the nightly copies on disk (`latest_file` is `hub-YYYYMMDD-HHMMSS.sqlite.age` since 2026-11-05). `due_next` is the earliest unacknowledged reminder at or after now, else the most overdue one. `avg_latency_ms_24h` averages successful calls and is null without any.
- `GET /metrics/proof?days=14` → `{ days, from, to, rows: ProofRow[], totals, friction }` for the proof run, one row per local calendar day (`EA_TZ`), oldest first, today last. `days` is 1 to 90.

```
ProofRow = {
  day: "YYYY-MM-DD",
  captures_created, captures_auto_sorted, tasks_done,
  reminders_fired, reminders_acked, reminders_snoozed,
  logs_created, notes_edited, ai_calls, health_logs: number,
  now_at_0900: boolean | null,
  next_or_doing_eod: number
}
```

  `captures_auto_sorted` counts captures processed that day with `sorted_by: auto`. `tasks_done` uses `done_at`, else the time the status changed. `reminders_fired` counts `fired[]` entries, `reminders_snoozed` counts `snooze_log[]` entries, `reminders_acked` counts reminders whose `acknowledged_at` was written that day (a repeating reminder counts once per day). `notes_edited` counts notes whose `title` or `body` was written that day. `now_at_0900` is `true` when some task is in `next` or `doing` now and has held that status since before 09:00 local that day; the hub keeps no status history beyond the field timestamps, so when that cannot be shown it is `null` and `next_or_doing_eod` (tasks in `next` or `doing` at the end of that day, now for today) is the fallback. `totals` sums the counters and adds `days_with_now_at_0900` and `days_now_unknown`. `friction` is `{ captures_stale: [{ id, text, created_at, age_h }], reminders_snoozed_3plus: [{ id, title, snoozes }], tasks_parked_7d: [{ id, title, parked_since, days }] }`: unprocessed captures older than 24 h, reminders snoozed three or more times in total, tasks parked for more than 7 days.

### Errors
JSON `{ error: string, detail?: any }` with 400, 401, 404, 409, 413, 422, 500. Invalid JSON or a JSON body that is not an object is always 400. Request bodies over 2 MB and vault files over 1 MB are 413.

## 4. Client obligations

1. Register once, store `device_id` and the token.
2. Keep a local store of entities with `seq` cursor. On start and on `change` events: pull `/sync/changes` until `more` is false.
3. Every local edit becomes a Patch in the outbox and is applied locally immediately. Flush the outbox whenever online. On conflict (hub rejects), reload the entity.
4. Compute local notifications from tasks with `remind_at` (`snoozed_until`, `repeat`) so they fire with no network. Also listen to `notify` on `/live` when connected.
5. Apply the style rules locally only for display; the hub is the enforcer for AI output.
6. Never store work-space entities in any file that leaves the device (no vault, no export).

## 5. Hub obligations

1. SQLite, WAL mode, FTS5. Tables: `entities`, `changes`, `devices`, `sessions`, `ai_calls` (audit: backend, model, redactions, tokens, ms).
2. Reminder loop every 30 s: fire open tasks whose reminder time (counting a snooze) has passed and that were not already fired for that time; emit `notify` with the task id; record in `fired` (silently, no change row).
3. Vault directory on disk is the file source of truth for notes; the DB row is the index. Writing a note entity writes the file; writing the file updates the entity.
4. AI pipeline: load facts (non-private if cloud), active rules, open ledger for the session, project resume card if any; build system prompt; redact; call backend; apply filter rules; append to ledger if `task_type = troubleshoot`.
5. Redaction patterns (minimum): `-----BEGIN ... PRIVATE KEY-----`, `AKIA[0-9A-Z]{16}`, `sk-[A-Za-z0-9_-]{16,}`, `xox[a-z]-`, `ghp_`, `password\s*[:=]\s*\S+`, `token\s*[:=]\s*\S+`, `Bearer\s+\S+`, email addresses when `space = work`, any `fact` with `private: true` by value match.
6. Style filter (always on, after generation): replace em and en dashes with a comma, colon or period as fits (default: comma); remove emoji in code blocks; strip closing filler lines matching `^(let me know|feel free|hope this helps|if you have any)`; strip opening platitudes matching `^(great question|good question|absolutely[,!])`; replace `let me know if` sentences with nothing; refuse the phrase `final fix` (rewrite to `this change`); every `rule` with `enforce in (filter, both)` and a `pattern` is applied as a regex replacement.
7. Backups: Litestream to `storage` when configured, and a nightly `VACUUM INTO` copy to the backup directory with 30-day retention. Every copy that leaves `hub.sqlite` is encrypted with age to the backup key (see Backups and encryption at rest).
8. Knowledge sweep at 03:10 local every night (and on demand with the `sweep` command): recompute `links` for every personal note and rule-based `suggested_tags` for notes without tags, and `project_id` for notes in a project's folder that have none, writing only what changed and never rewriting vault files; then drop repeated phones and emails on people and merge people that are surely one (see People).
9. Per-request log line: method, path, status, duration, and the device id when the request carried one. Never the query string, headers, tokens or bodies.

## Image generation (shared image service)

The hub is a client of the shared image service (a separate gateway on the owner's network; see `docs/image-generation/`). `EA_IMAGE_SERVICE_URL` and `EA_IMAGE_SERVICE_TOKEN` (hub env only; devices never see the token) turn it on. Every request passes the service's own validation: explicit controls are requirements, and an unsupported or conflicting one is refused with `422 { error: "plan_rejected", detail: [{ field, code, message }] }`, never silently changed.
- `GET /images/capabilities` → `{ enabled: false }`, or `{ enabled: true, api_version, workflows, unavailable_features, workers, controls, hardware }`. `hardware` (since 2026-11-05) is `[{ id, label }]`, the service's workers a person or the assistant may pick by hand, from `EA_IMAGE_WORKERS` (`id=label` pairs separated by commas; empty by default, and then only Auto); clients build the Hardware picker ("<label> only") and name a job's or gallery image's worker from it, showing the id when it has no label.
- `POST /images/plan` (dry run) and `POST /images/jobs` (header `idempotency-key` optional) body `{ prompt, operation?: "generate" | "edit", references?: [hub image id], width?, height?, aspect?: "1:1" | "4:3" | "3:2" | "16:9" | "9:16" | "match_source" | "W:H", realism?: "from_prompt" | 0..100, seamless?: "off" | "x" | "y" | "xy", transparent?, quality?: "auto" | "fast" | "best", hardware?: "auto" | <a worker id from `hardware` in capabilities>, count?: 1..4, seed?, exact_prompt? }`. The plan shows the exact output and generation sizes (and any disclosed crop), the workflow and model, the original and adapted prompt, eligible workers and notes. `count` makes that many individually tracked jobs.
- `GET /images/jobs?limit=` (this project's history), `GET /images/jobs/:id` → `{ id, status: queued | running | succeeded | failed | canceled, status_label ("Waiting: protecting gameplay", "Running on Desktop GPU"), reason, progress, error, measured, plan, image_id? }`. A finished job's result is copied into the hub's image store, served by `GET /ai/images/:image_id`. `POST /images/jobs/:id/cancel` cancels only this project's job.
- Assistant tool `generate_image`: submits, waits up to two minutes, and the images show under its reply (`reply_images` in the chat response; stored as `images` on the assistant turn).
- **People** (`person` entities): `{ name, given_name?, family_name?, nickname?, organization?, job_title?, birthday? (YYYY-MM-DD or --MM-DD), dates: [{ label?, date }] (anniversaries and other labeled dates, same format), phones: [{ label?, value }], emails: [{ label?, value }], addresses: [{ label?, street?, city?, state?, postal_code?, country? }], relationship? (app only), apple?: { id, device, me? } (`me`: the owner's own card, My Card on the Mac), merged_into? (on a deleted duplicate: the person it was merged into) }`. Mirrored both ways with Apple Contacts by the one device where Settings, People, "Sync Apple Contacts" is on (`apple.device` is that device's id; other devices leave linked people alone). Rules (`ContactsMirror`): a card not in the app becomes a person; a person made in the app gets a card, or is linked to an existing card with the same name and merged; a change on one side since the last agreed snapshot is copied to the other, the app winning when both changed, and with no snapshot yet both sides' values are kept; labels, phone formatting and a value listed twice (Apple repeats a number once per linked card) are not differences. Deleting a person unlinks it and never deletes the card (that card is then not imported again), except a duplicate merged into another person (`merged_into`): its card is removed once the kept person's card holds every phone, email, address and date on it, and My Card is never removed; a card deleted in Apple Contacts removes the person, but only on a device that saw it before. What the owner knows about someone is a `fact` with `person_id` (or `person`, a name, when they are not in People yet; those join the person once they exist); a fact whose value names them the same way Related matches names (one about a group of friends) counts too, after the linked ones. Duplicates: `POST /people/merge` `{ keep, merge: [ids] }` joins lists by value (an address by street, city and postal code, or by state and country when it has none of those), fills empty fields from the others, moves their facts to the kept person (linked ones, and ones kept with a duplicate's name that nobody outside the merge is also called) and deletes the others with `merged_into` (the kept person takes a duplicate's Apple link when it has none); the nightly sweep (only for people linked by a device that reports the feature `contacts-merge` in its `device` entity's `features`, which the syncing device sets after its first contacts run with a build that understands this, since an older build would write the repeats back) drops repeated phones and emails and merges people that are surely one (the same given and family name, or whole name, plus a shared phone or email, or one with neither, or two organization cards of the same company: no given or family name, named by their `organization`), keeping the `me` person, else the fullest. Assistant tools: `people` (look up, with known facts), `save_person` (create or change; phones, emails and addresses are added by value). `save_person` by name and `remember` with `person=` write to someone only when the name is theirs alone and whole (full name, nickname, or given and family name, then a given name, family name or first word of the name; any script, accents ignored); a name two people have is an error naming both with their ids, and a name nobody has is a new person (save_person) or a fact kept with that name (remember), `merge_people` (keep, merge), `remember` with `person=` (a key matches an existing fact only about the same subject, the owner or that person, and separators in keys are ignored, so `focus:2026-10` and `focus_2026_10` are one fact).
- **Image Gallery** (`image` entities, synced like any kind): `{ image_id, source: generated | attached | uploaded | downloaded | photos, title?, width?, height?, mime?, bytes?, prompt?, caption?, job_id?, workflow?, worker?, seed?, session_id?, saved_to_photos? }`. Bytes are in the hub image store (`GET /ai/images/:image_id`). Two bins: Generated (`source: generated`) and Saved (the rest). The hub files a finished job itself (on `GET /images/jobs/:id`, which then also returns `gallery_id`, and every 20 s from the service's job list), once per job; a record the owner deleted is never brought back. A picture attached in a chat is filed as `attached` with its `session_id`; deleting that chat blanks and deletes the record too. A picture the owner uploads or attaches again after deleting it from the gallery is filed again (a new record). Deleting a chat never removes the bytes of a picture a gallery record keeps (generated, saved or uploaded). `POST /images/library?source=uploaded|downloaded|photos&name=` with the raw image as the body (25 MB at most, PNG, JPEG, GIF or WebP) files a picture in Saved and returns the entity. Delete with `DELETE /entities/:id`. Any `image_id` can be a reference for `/images/plan` and `/images/jobs`.
- Phone photos for the assistant: `/ai/chat` and `/ai/chat/stream` take `device: { photos: true }` from the iPhone app when full photo library access is on. The tool `phone_photos` (`count` 1 to 6, `since_days`) then sends the SSE event `photos_request { id, count, since_days? }` and waits up to 60 s; the phone answers `POST /ai/photos/:id` with `{ photos: [{ b64, taken_at?, width?, height? }] }` (newest first, 1024 px JPEG; 410 when nothing waits any more). The model sees the photos with the tool result; they are stored with the chat (under the reply), so deleting the chat erases them. Without `device.photos` the tool explains how to turn access on.
- Apple clients: Settings, Images has "Save created images to Photos" (images made after it is turned on, once each; `saved_to_photos` marks them) and "Full photo library access" (the gallery gains a Photos bin; a photo is uploaded only when used or added).

## Privacy rules every module meets

Since 2026-11-05 (rule 6 of `docs/05-public-release.md`; the reasons are in `docs/06-threat-model.md`). A module, new or changed, meets every rule before it is merged. Where a rule names a test, that test enforces it.

1. **Data stays on the owner's devices.** A module's data lives in the hub's data folder and in the caches of the devices the owner set up. Nothing goes to the project or to a server it runs; there is no relay.
2. **Nothing leaves the hub until the owner turns it on.** A module contacts an outside address only after the owner turned on that module and the setting that needs the address (a sign-in, a key, an address they typed). Nothing is contacted on its own at hub start or app launch. Every outside address is listed in `docs/privacy-network.md` with what causes the contact and what is sent (`hub/test/no-phone-home.test.ts`).
3. **Devices talk to the hub only.** A picture or file from another site reaches devices through the hub (`GET /games/art/:appid` serves Steam's game pictures this way). A picture in text that points to another site is shown as a link and never loaded on its own. No web fonts, CDNs, link previews or favicons from other sites.
4. **Cloud models only when a request allows it.** Then work items and private facts are taken out and keys redacted first (section 5). Work items never leave the owner's machines.
5. **Logs hold ids, counts, kinds, durations, status codes and module names.** Never a token, key, password, cookie, Authorization header or an address carrying `?token=` or `?key=`, and never personal text: captures, notes, note file names, titles of tasks, events, reminders or people, mail subjects or senders, chat messages, model prompts or replies, search words, command output. An error is logged as `errCode(e)` and an address as `logHost(u)` (`hub/src/logsafe.ts`), never with its message: an upstream answer can echo the request (`hub/test/log-privacy.test.ts`).
6. **Copies are encrypted.** Any copy of a module's data that leaves the data folder (a backup, a replica, an export kept on disk) is encrypted with age to the owner's recovery key (being built). Chats, the work key, sign-ins and `hub.env` are never copied. Device caches use the operating system's strongest file protection.
7. **Secrets stay on the hub.** A key, token or password a module needs is typed into the app, kept only on the hub, never sent to a device, never shown again, and never written into a log, a note, a record or a backup.
8. **Permissions only for chosen modules.** A device asks for an operating system permission (microphone, speech, photos, contacts, calendar, reminders, health, location, notifications) only for a module the owner chose, after setup or when that module is first used, never at launch. Speech is recognized on the device.
9. **No third-party SDKs or analytics.** No analytics, crash reporting, advertising, tracking or telemetry in the hub or any app, and no update check the owner did not ask for.
10. **Open-source licenses only.** Every dependency, and every model the setup suggests, has an open-source license (MIT, ISC, Apache-2.0, BSD or MPL-2.0; GPL or AGPL only for a separate service, such as SearXNG). It is checked before it is added.
11. **Kept only as long as chosen.** Chats and host command output are kept forever unless the owner sets a number of days (`GET /settings/retention` → `{ chat_keep_days, command_output_keep_days, choices }`; `PUT /settings/retention` with either, whole days 0 to 3650, 0 is forever; `<data>/retention.json`, `hub/src/retention.ts`). Once a night at 03:40 older chats are deleted the way deleting a chat in the app does it, and older command output is cleared (the command, its result code and its journal entry stay). A hub with no setting deletes nothing. A new hub's Welcome page offers 90 days for chats and 30 for command output.
12. **Captures are never searched.** Filing a capture runs with no web tools and no web instructions (`ChatInput.no_web`), whatever Web lookups says, so a diary line never becomes a search query or a page fetch. Photos from the phone (`phone_photos`) are shown only to the hub's own model, never to a cloud model.
13. **Device privacy choices.** Each device keeps a privacy choice per item in Settings, Privacy on this device, all off by default: Include in iCloud Backup (iPhone, iPad), Show in Spotlight (titles only, never note text), Show titles on the lock screen (widgets, Live Activity; Watch complications follow the Watch's own default, off).
14. **A removed device forgets.** A device told `device_removed` deletes its local copy: the sync store or IndexedDB, unsent edits, the widget snapshot, chats, caches and Spotlight entries; it keeps only the hub address and theme.
15. **Keys travel in headers.** Hub files (`/wiki/media/...`) are fetched with the key in the Authorization header, never `?token=`. A hub address typed without a scheme is https, except loopback. Pairing links write a space in the device name as `%20`, and clients also read `+` as a space.
16. **Browser features say whose they are.** In the web and Windows apps, Talk (the browser's speech recognition) and Use my location (its location service) each ask once and name the company first; answers are read aloud only with on-device voices; the bill splitter's state picker needs neither.
