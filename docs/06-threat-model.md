# 06. Threat model

Written 2026-11-05 and checked against the code that day, then updated the same day once Phase 2 of `docs/05-public-release.md` was built (branch `release-phase-1-2`; the owner's own hub runs it once it is deployed). Each control is marked:

- **Built**: in the code now.
- **Not built yet**: planned, with the phase that builds it.

Anything else that is missing is listed under "Known gaps". The standard is rule 6: everything the project controls is private and encrypted, reaches only the devices the user set up, and holds up to a careful Tor user at DEF CON. Every outside address is in `docs/privacy-network.md`. The rules each module meets are the last section of `packages/shared/CONTRACT.md`.

## The system

One hub (Node and SQLite) runs on a machine the owner controls. Devices talk only to it: the iPhone, iPad and Mac apps, the Watch (through the iPhone), the web app in a browser or on the home screen, and the Windows app. Devices reach the hub in one of three ways chosen at install: Direct link (iroh, the default), Tailscale, or the home network in LAN mode. The hub can copy backups to a second machine the owner controls, talk to model servers (local by default, a cloud model only when allowed) and read services the owner signs in to.

## Controls

| Control | State | What it does |
|---|---|---|
| Direct link (iroh) | Built | Each device connects to the hub's key from the pairing QR code, encrypted end to end (QUIC with TLS 1.3 keyed to that key), and accepts no other key, so a relay cannot stand in for the hub. When no direct path exists, n0's relay passes the encrypted traffic; it sees IP addresses, keys and timing, not content. Requests over it count as a remote device and need that device's own key (`hub/src/link.ts`). If n0's relays stop, Direct link stops until the hub moves to another relay (`EA_LINK_RELAYS`) |
| Tailscale (WireGuard) | Built | Devices reach the hub through an encrypted tunnel. The hub listens on `127.0.0.1` and Tailscale Serve gives it HTTPS with a certificate for its `*.ts.net` name |
| HTTPS off Tailscale | Built | In LAN mode the installer makes a self-signed certificate and the hub serves HTTPS; plain HTTP is answered only on 127.0.0.1 (`hub/src/tls.ts`). Pairing links carry the certificate's SHA-256 (`fp=`) so a device accepts that certificate and no other |
| A key per device | Built | Each device gets its own key through a pairing code that works once and expires in 10 minutes (`hub/src/devicekeys.ts`). The hub keeps only each key's SHA-256. No link or QR code holds a lasting secret, and any device can be removed on its own. The hub's main key (`EA_TOKEN`) stays in hub.env for the hub's own scripts; a device that still holds it trades it for its own key on its next sync |
| Token checks | Built | Compared in constant time. Failed tries from one caller are slowed, up to 5 s each |
| One-door keys | Built | The calendar feed key reads the calendar feed only, the sensor key posts readings only, the feed token posts project and wiki feeds only |
| Work items sealed | Built | AES-256-GCM with the entity id as associated data (`hub/src/workkey.ts`). The key file is kept apart from the database and in no backup. Erasing the work space destroys the key, so every older copy holds work items nobody can read. Work items never go to a cloud model or into a file that leaves a device |
| Chats kept apart | Built | `chats.sqlite` is never backed up (`hub/test/privacy.test.ts`). Deleting a chat deletes its photos |
| Mail kept apart, shown safely, changed only by what the owner does | Built | `mail.sqlite` is never backed up, synced or open to the assistant's tools; mail that left the Inbox (or, for the other folders kept since 2026-11-20, its folder), done mail after 30 days, a mailbox unlinked or the module switched off is deleted with `secure_delete` and a WAL checkpoint, so it leaves the disk (`hub/test/mail-inbox.test.ts`, `hub/test/mail-routes.test.ts`); a refresh that is reading a mailbox at the moment it is unlinked or its Mail switch goes off keeps nothing of what it read, and an account's password stays only while Receipts and renewals, the Mail screen or calendar sync uses it (`hub/test/mail-accounts.test.ts`). A mail's HTML is rebuilt from an allowlist and shown only in a frame where no script runs, loading nothing (`hub/test/mail-html.test.ts`); a sender's logo only when iCloud verified it (`hub/test/mail-logos.test.ts`). The pictures a mail shows from the web are fetched only through Tor, https only, never its 1 by 1 or hidden ones; a hub without Tor fetches none until the owner presses Show pictures on a mail (`hub/test/mail-tor-fetch.test.ts`, `hub/test/mail-routes.test.ts`). A crafted mail cannot hold the hub: its markup, its CSS and the sender's data for cards are read in one pass each, however much of it never closes, and a mail the reader fails on is shown as text without stopping the refresh (`hub/test/mail-hostile.test.ts`, `hub/test/mail-cards.test.ts`). Nothing in a mail can give a link a tooltip other than the address it goes to, a mailto link keeps only its addresses, subject and body, the pictures one mail holds have a limit in all however often one is shown, and its frame is at most 30,000 px tall (`hub/test/mail-html.test.ts`, `hub/test/mail-routes.test.ts`). The only writes to a mailbox are Done's IMAP `MOVE` between the Inbox and the archive folder, Delete, Spam, Not spam and Move to's `MOVE` to Trash, Junk, the Inbox or one of the owner's folders (never a folder a request names by path, never Drafts, Sent or Archive, nothing erased; `hub/test/mail-move.test.ts`) and the read and pin flags (`\Seen` and `\Flagged`, no other), each to a kept, re-checked message (`hub/test/mail-done.test.ts`, `hub/test/mail-seen.test.ts`, `hub/test/mail-pins.test.ts`), and a draft the owner wrote and saw whole, `APPEND`ed to Drafts: its recipients are addresses the owner typed or, for a reply, the kept mail's From (never its Reply-To), no value can start another header (a long header folds only between its items), and a Bcc is only ever an edited draft's own, so nothing in a mail or a request can add a recipient (`hub/test/mail-drafts.test.ts`, `hub/test/mail-files.test.ts`). Since 2026-11-24 the owner can send that same mail: built by the same code, so the same rules hold for whom it goes to; only the owner's Send on the Mail screen sends (`/mail/send` and the outbox are closed to the assistant's tools, and no tool writes mail); it waits 10 seconds for Undo, is claimed in one statement and marked sent the moment the server has it, so a restart sends it once and never twice; a Bcc is in the envelope only, never in the message or its copy in Sent; a refused recipient means nobody gets it; a Read only mailbox never sends; the sending server is the account's own (fixed for iCloud and Gmail, typed by the owner for another server, checked once before it is kept), with TLS always, the certificate checked against its name and no address on the owner's network; a failure leaves the mail in the outbox with the hub's words for why, never lost (`hub/test/mail-send.test.ts`). Attachments are read only when the owner opens a mail (previews of small pictures, whose bytes must be a picture), presses Download, or saves a forward or an edited draft that carries them (only a part the message lists as an attachment, served as a file to save with nosniff and a sandbox, never as a page), from a re-checked message, and never kept; the screen warns before a file that can run programs (`hub/test/mail-attachments.test.ts`). Triage runs only when the owner asks for it (Sort new mail), as all of the hub's own model work does; only a hub set to `EA_BACKGROUND_AI=auto` runs it after a refresh. It asks the local model, never a cloud one, about each waiting mail with nothing of the owner's but their name, takes only a known urgency, a yes or no and one line of plain words from it, and keeps that a week; switched off, it stops and keeps nothing (`hub/test/mail-triage.test.ts`). Unsubscribe uses only the mail's own header (https without a login, or a plain mailto), never an address from a request; its one POST goes through Tor, or, without Tor, only when the owner accepts that the sender sees the home's address and only to a public address, so a mail cannot aim the hub at the home network; blocking moves a sender's mail to Junk with the same fenced `MOVE`, and is refused for the owner's own address, a mail provider's whole domain and an ending many sites share (`hub/test/mail-unsubscribe.test.ts`, `hub/test/mail-review-fixes.test.ts`). The other folders (Drafts, Sent, Junk, Trash, the owner's own) are read the same read-only way and shown the same safe way, with no web picture fetched and Junk's mail marked as spam (`hub/test/mail-folders.test.ts`). The local model may write only a reply's greeting and sign-off and up to three short suggested replies, from the owner's name and the thread (no memory facts, no addresses), and the hub takes only short plain words from it (no link, address, site name or long number, in any form of letters and digits), so a hostile mail cannot put a link, an address or a number into a reply; the owner sees, edits or drops both before saving (`hub/test/mail-drafts.test.ts`) |
| Backups written safely | Built | Written whole, then renamed; mode 600; a damaged copy is skipped |
| Backups encrypted | Built | Every nightly backup, the settings, gallery and recording copies sent to the backup host, and the Litestream replica are encrypted with age to the hub's backup key (`hub/src/backupkey.ts`); the owner saves its recovery key in a password manager from the Welcome page. The nightly copies need only the key's public half. Litestream reads back its own uploads, so it holds the private half while it runs, passed in its environment from the key file and never written to a config file |

| Cloud models opt-in | Built | Off by default (`EA_ALLOW_CLOUD_DEFAULT=false`). A request must allow the cloud. Work items and private facts are taken out and keys, tokens and passwords redacted before it leaves |

The installer sets up a local SearXNG at a pinned commit and its own Tor for SearXNG and the page reads, without asking (`EA_TOR=0` skips it) | The assistant searches through the owner's own SearXNG and reads public pages only |
| Host commands | Built | Reading commands run at once; anything that changes a machine, reads a secret file or uses a password manager secret waits for the owner's approval. Secrets are referenced by name and taken out of command output |

| Logs without secrets or personal text | Built | `errCode` and `logHost` in `hub/src/logsafe.ts`, checked by a test over every log call |
| Nothing phones home | Built, apart from the Apple gaps below | `docs/privacy-network.md`, checked by `hub/test/no-phone-home.test.ts` |

## Adversaries

### Someone on the same network
A café or hotel network, or a guest on the home network.
- Protected (Built): on Tailscale every byte between device and hub is WireGuard, and the hub port is not open on the network at all.
- Protected (Built): in LAN mode, HTTPS with a pinned certificate, so a device notices a machine in the middle.
- Gaps: the web app in a browser cannot pin; it shows the browser's warning for the self-signed certificate and relies on the person checking it. A model server reached over plain HTTP on the home network (not the tailnet) is readable.

### A stolen or lost phone, locked
- Protected (Built): iOS encrypts the app's files; after a restart nothing is readable until the passcode is entered. The Watch holds no hub address or token.
- Protected (Built): the owner removes that one phone from another device and its key stops working; the other devices carry on.
- Gaps: the app's files use iOS's default protection, readable by forensic tools once the phone has been unlocked since it started (Phase 2 lists complete file protection for the phone, Watch and Mac caches). The hub token sits in the app group's settings file, not the Keychain, so it is also in an unencrypted Finder or iTunes backup of the phone. Until per-device keys land, losing a phone means changing the token on every device (`deploy/RUNBOOK.md` J4).

### A stolen hub disk
- Protected (Built): the disk encryption check, so the owner knows the disk is encrypted at rest; age-encrypted backups in the backup folder.
- Gaps: without disk encryption, everything is readable: the database, chats, `connections.json` (the sign-ins and the built-in vault's master password), `hub.env` (the hub's main key and cloud keys) and the notes folder. The work key and the backup key are on the same disk, so sealed work items and the backups are readable too. `connections.json` and `ai.json` are sealed with `secrets.key`, which keeps them out of anything that copies the data folder alone (a stray rsync, a folder image, a support bundle), but that key is on the same disk, so only disk encryption protects them from someone holding the disk.

### A compromised backup host
- Protected (Built): chats, the work key, `connections.json` and `hub.env` are never copied there, and work items arrive sealed.
- Protected (Built): every database copy, settings file, gallery picture, recording and the Litestream replica is age-encrypted before it leaves the hub, so the host holds only ciphertext it cannot open.
- Gaps: copies written before this change stay plain on the host until the owner removes them (`deploy/RUNBOOK.md` F9). Encrypted or not, the host sees file sizes and times, and can delete or withhold copies, so a restore drill (`deploy/restore-drill-user.sh`) stays the check that backups work.

### A rogue device on the tailnet
A machine of the owner's that is compromised, or a device that still holds an old token.
- Protected (Built): the hub answers nothing without a valid key, and failed tries are slowed. Tailscale's access rules can stop other tailnet machines reaching the hub's port at all.
- Protected (Built): every device has its own key, so an old device is removed by itself, and a pairing code is useless after one use or 10 minutes.
- Gaps: the hub's main key still opens everything, and links and QR codes made before 2026-11-05 carry it, so it should be changed once every device has its own key. The model servers on the tailnet (Ollama on another machine) take requests from any tailnet device without a key.

### Cloud model providers
- Protected (Built): nothing goes to a cloud model unless the request allows it, and then work items and private facts are taken out and keys, tokens and passwords redacted. The default model is local.
- Gaps: when the owner allows the cloud for a chat, that chat, the memory facts that are not private and the tool results go to the provider by design, and the provider's own retention rules apply. Redaction is by pattern, so a secret in an unusual form can pass.

### The services the user signs in to
Google, Atlassian, Steam, Letterboxd and the password managers.
- Protected (Built): each sees only what its own API returns to the hub, plus the hub's address and when it calls. Gmail access is read-only and mail is read by the local model, never sent on. Sign-in secrets stay on the hub; devices see only whether a service is linked.
- Protected (Built): the owner's own app or key for each service, with no relay of the project's in between. The guided screen for making one is Phase 3.
- Gaps: Steam's API takes the key and Steam ID in the address. The Apple app's sign-in sheet shares Safari's cookies with the service.

### Someone holding an unlocked device
- Protected (Built): a change on a machine waits for an approval tap, and work items can be erased with their key.
- Protected (Built): the owner can remove that device's key from another device.
- Gaps: whoever holds the unlocked device can do everything the owner can, approvals included; there is no app lock (Face ID or a PIN) in the Apple, web or Windows apps.

### A poisoned dependency
- Protected (Built): `package-lock.json` pins every npm package with its hash and installs use `npm ci`. The hub names 11 runtime packages and the web app 13 (each pulls in more); the Apple apps use no third-party packages. Licenses are checked by hand today.
- Protected (Built): the Windows hub installer carries Microsoft's Visual C++ runtime installer for PCs without the
  runtime. It is used only when its Authenticode signature is valid (unchanged, from a certificate Windows trusts) and
  both the signer and its issuer are Microsoft Corporation, and the file says it is the x64 Redistributable 14: checked
  at build time and again right before it runs as an administrator (`Test-VcRedistFile` in `deploy/install.ps1`).
- Gaps: a bad update runs with the hub's full access: every record, every key, and SSH to the owner's machines. The user service the owner runs is not sandboxed the way the system unit is. Phase 5 adds a license and source check (cargo-deny for the Windows app's Rust crates) to the build.

### Content that carries instructions
A mail, a web page, a wiki page or a shared article written to steer the model.
- Protected (Built): mail is read by a background job with no tools. Changes on machines wait for approval. Pictures in model replies, notes, the journal and wiki pages are links and load nothing on their own, so text cannot send data out by naming a picture. Page reads refuse the owner's own network.
- Gaps: a capture is filed by a chat that can read web pages, so a captured or shared text that names an address could make the model read it, with data in the address.

### A helper, or someone holding the helper's account
Someone the person trusts fully helps with their devices ([helpers.md](helpers.md)). The person is never asked about a
command, by design: so whoever controls the helper's hub can run commands as the person on their computer and sign in to
their home devices with the passwords they saved for the helper.
- Protected (Built): the person says yes once and can Stop at once (the key ends that moment). The helper key opens
  `/warden/*` only, never the person's notes, chats or diary, and only from the same machine. Only the SHA-256 of the key
  passes through the root service; the key itself is sealed with the helper hub's secrets. Commands that change anything
  wait for the helper's own yes in the chat, and every check, change, scan and saved password is written in the person's
  log with the exact command. Saved passwords live in a vault of their own, are filled in on the person's hub, and are
  cut out of the output. SSH goes only to private addresses, and a device's key is kept from the first sign-in, so a
  stand-in device gets no password. Commands run as the person, without administrator rights.
- Gaps: a helper hub taken over by someone else can do everything the helper can until the person presses Stop; the
  log shows it afterwards, not before. The person's Windows app turns on Start on login the first time they are helped,
  so after a restart it answers the helper again without them opening it; it says so on People who help you. The first SSH sign-in to a device trusts whatever key answers. The machine's admin
  can read the person's files anyway, as for every person on the machine.

## Known gaps

1. The hub's main key still opens everything, and links made before 2026-11-05 carry it: change it once every device has its own key.
2. The live database, chats, notes and sign-ins are plain at rest unless the disk is encrypted (the hub checks and says so; sign-in keys encrypted at rest is Phase 3).
3. The web app cannot pin the LAN certificate; it relies on the browser's warning.
4. Device caches: default iOS file protection, the Apple token outside the Keychain, the web and Windows apps' token in IndexedDB.
5. No app lock on any device.
6. The Apple apps load Steam pictures and outside wiki pictures from other sites, and dictation can use Apple's servers (`docs/privacy-network.md`).
7. The web app has no Content-Security-Policy.
8. The user service runs without the system unit's sandbox.
9. Several people on one machine (`docs/multi-person.md`): each hub's files are readable only by its own account, but anyone with admin (root or sudo) rights on the machine can read every hub's database, notes, chats and keys, and the machine owner usually has those rights. The app says so before someone is added and after; only encryption with a key that never reaches the machine would close this.

### Other mail accounts (since 2026-11-22)

The Mail screen can link Gmail or any IMAP server with an app password. The owner types the server, so the hub now connects to a host it did not choose itself. Mitigations: only the owner can link (the `/connections` writes are closed to the assistant and helpers); a name, never an address, is taken; at each connection the name is looked up and refused when any address is on the owner's own network (private, loopback, link-local, and IPv4 inside IPv6 in every form: mapped, compatible, NAT64, 6to4, a long spelling), and the hub connects only to a checked address, so DNS answering differently a moment later cannot point it inside the home; TLS on connect only, the certificate checked against the name; the password is sealed with the other connections and sent only to that server. A hostile server can still send any mail it likes, as any sender can, so the Mail screen's safety rules all apply; and brand logos, which trust a verdict iCloud writes on each mail, are never taken from these accounts, because there a sender could write that verdict.

### Sending mail (since 2026-11-24)

The Mail screen sends: Send puts the mail in the hub's outbox, and 10 seconds later the hub hands it to the mailbox's own sending server with the account's app password (`smtp.mail.me.com` for iCloud, `smtp.gmail.com` for Gmail, the server the owner typed for another account). What a sent mail could do that a draft could not is reach someone, so the risks are a mail sent by something other than the owner, sent to someone the owner did not choose, sent twice, half sent, or lost. Since 2026-11-24 the assistant can also write a mail (`propose_mail`) for the owner to send with one tap from a card in the chat: the owner declined letting it send by itself. A page, a mail or a document the model read could try to steer it into writing to someone else or saying something else. Mitigations for that: the tool keeps a proposal and sends nothing; Send is a route of the owner's that the assistant's tools can never reach (`/mail/proposals`, `hub/src/ai/api-guard.ts`); every recipient must be in the owner's own messages in that chat or be an email of a person in People, so an address the model read anywhere else is refused; the card shows the whole mail, From, To, Cc and Subject before Send, with the same 10 seconds of Undo; the tool, its description and the tool guide tell the model that nothing is sent until the owner taps Send, and a reply that claims otherwise gets the plain sentence added; one per reply; never while a capture is filed; a proposal is deleted 24 hours after it was made, sealed while it is kept (`hub/test/mail-proposals.test.ts`). Mitigations: only the owner's Send on the Mail screen sends (the route and the outbox are closed to the assistant's tools, `hub/src/ai/api-guard.ts`, and no tool writes mail); the mail is built by the same code as a draft, so its recipients are only the addresses the owner typed, a reply's sender (never its Reply-To) and Reply all's people read from the mailbox, and no header can be injected; the owner sees it whole (Preview) before Send, and has 10 seconds of Undo; a Bcc (only ever an edited draft's own) goes in the envelope, never into the message or its copy in Sent; when the server refuses any recipient the message is never handed over, so nobody gets it; a mail is claimed in one statement and marked sent the moment the server has it, before the connection closes, so a hub that restarts in the window sends it once, and one that stops while sending never sends it again by itself (it shows as not sent, and says to look in Sent); a refused password, a refused address or a server that does not answer leaves it in the outbox with the hub's own words (never the server's), until the owner tries again, takes it back, saves it as a draft or discards it; a Read only mailbox never sends. The connection: TLS from the start or STARTTLS that must take, the certificate checked against the server's name, every address the name answers checked (none on the owner's network) and only a checked one connected to, the hub named `[127.0.0.1]` in its greeting, hard time limits on every step and on the whole send. A sending server the owner types is a name, never an address, signed in to once before it is kept; a guess from the IMAP server's name is only a hint in the empty field and is never connected to. While it waits, the message is sealed with the hub's sign-ins key in `mail.sqlite`, never backed up or synced, and cleared once sent (`hub/test/mail-send.test.ts`).
